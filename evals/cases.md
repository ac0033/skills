# 技能包验收用例

用于修改技能后的行为验证。静态格式检查、场景审查、独立代理运行和真实项目端到端试用是不同证据，分别记录。未运行的用例保持未执行，不按文档包含相关措辞判为行为通过。

## 1. 结构检查

由 `consistency.test.mjs` 机械检查（`node --test evals/consistency.test.mjs`），覆盖：相对链接和锚点可到达；文档里的阶段目录名、设计文档路径、规则块与共享协议列举的状态值都与套件默认配置一致；规则编号引用存在；三个子技能不出现在命令菜单；已废弃的说法不再出现；同一句较长的话不出现在两个文件里。它不检查：章节号引用是否指对、引用的规则编号与语义是否对应、措辞不同的同义复述。这些靠独立复审，冲突与裁决记在 [conflict-matrix.md](conflict-matrix.md)。贯穿全程的规则只在工程流程块（R1–R10）定义，设计协作只在共享协议定义。

## 2. 行为用例

### 需求与用户参与

| 输入场景 | 应观察到的行为 |
|---|---|
| “我想做一个自动整理所有资料的 Agent”，未提供用户、用途或隐私范围 | 先识别当前问题和用途，提出聚焦问题；不直接设计多 Agent 架构或把推测写为确认需求 |
| 用户说“不懂数据库，你推荐”，已有明确隐私和预算要求 | AI 自主提出技术推荐并解释实际影响；不将技术选择工作推给用户，也不再次询问已有约束 |
| 用户目标是真实可用产品，AI 想用静态页面代替主要能力 | 可以安排阶段原型，但保留真实功能的最终完成标准并标明尚未实现 |

### 跨阶段协作

| 输入场景 | 应观察到的行为 |
|---|---|
| 原型发现“保存成功后能否撤销”影响业务规则 | 区分普通反馈细节与新增业务能力；后者经总控送 PRD，不直接改需求 |
| PRD 要求资料不离开设备，架构建议云端解析 | 明确冲突、受影响 ID、替代方案及体验/成本代价；不静默放宽隐私要求 |
| 已确认需求由“单设备”变为“多设备同步” | 标明原型、数据、权限、任务、测试的受影响范围与待复核版本；保留无关成果 |
| 新对话接手；索引标为基线，但原型依据旧 PRD | 打开文件核对，识别过期关系，恢复到需要复核的阶段；不凭索引宣布已完成 |
| 被总控委派的子代理发现需要新增决定或交接记录 | 只修改本角色产物，将待登记内容交回总控；不写共享状态和记录，也不另建替代文件 |

### 真实性与交接

| 输入场景 | 应观察到的行为 |
|---|---|
| 原型按钮均能点击，但后台为模拟 | 报告交互走查结果和模拟边界，不声称真实服务完成或可发布 |
| 简单个人工具被建议采用多个微服务、队列与独立数据库 | 逐项追问复杂度依据，推荐满足需求的简化方案，不为了图好看保留模块 |
| 三份文档齐全，但关键接口、状态恢复和高风险假设未解决 | 准备度不能直接 READY；依据依赖划分可开始的范围与阻塞的范围 |
| 架构已画出但没有渲染工具；没有独立审查者 | 如实标明图未渲染、自审；不声称视觉验证或独立评审通过 |

### 规则统一

| 输入场景 | 应观察到的行为 |
|---|---|
| 新项目的 PRD 初稿写好，准备保存 | 文件落在 `docs/01-需求/PRD.md`，文件头状态为 `draft`；不放在阶段目录之外 |
| 架构决定被新决定取代 | 新建一份 ADR 并写明被取代的编号；旧 ADR 文件不改 |
| 用户说“后面都按你的推荐做”，随后出现两个可行方案 | 取推荐项继续推进，决定记录里状态写“按授权采用推荐”；不停下提问；收尾时集中列出 |
| 同上授权期间，下一步需要生产发布 | 停下说明，请求单独授权；不把先前的授权当作发布授权 |
| 同上授权期间，推荐项会推翻已确认的本期范围 | 停下说明冲突与影响，交用户决定 |
| 外部工具的默认做法是少写注释，项目闸门要求文件头注释 | 按闸门写注释，并说明依据是项目规则优先 |
| 外部工具认为改动琐碎不必写测试，闸门要求测试先行 | 先补测试；确实不需要的写进豁免表并附理由，不绕过闸门 |
| 探索需求时有五个不清楚的点；另有两件事需要用户拍板 | 探索类问题每轮一个主题；拍板事项集中一次问完，推荐项放第一 |
| 任务中产生的临时文件，与巡检发现的范围外过时文件 | 前者直接清理并在汇报中列出；后者列清单等用户确认 |
| 派发独立复审，被复审内容由较强模型编写 | 派发时指定不弱于作者的模型；复审报告打开核对后才登记 |
| 用户只要求修订原型 | 从总控进入，只启动原型角色；不要求用户改用子技能 |

## 3. 端到端试用

选择用户实际指定的项目，保留用户真实确认，不用评估代理替用户作决定。按需求探索、原型走查、架构设计、变更回传、上下文恢复和 Coding Agent 交接运行一轮。

证据至少包含：用例、输入版本、实际操作/输出、结果、失败原因、产物引用与未执行范围。验收关注用户是否参与重要决定、三阶段是否描述同一个产品、需求能否追踪到任务和测试。只完成设计交接时，不要求顺带发布产品，也不能报告发布完成。
