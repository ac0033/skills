# 产品原型与交互验证

本技能由[产品设计总控](../product-design-orchestrator/SKILL.md)加载；被直接加载时，先加载总控，由它决定只启动原型角色还是走完整流程。

开始时读[共享协议](../product-design-orchestrator/references/shared-protocol.md)、项目状态、当前 PRD 及相关交接；产物采用[原型模板](../product-design-orchestrator/references/artifacts.md#prototype)。没有足够需求时先识别缺口，不能仅凭产品名称生成完整页面。

## 1. 结构与核心路径

先给出对产品目标、用户和本期范围的简短理解，再设计信息架构、导航及核心用户旅程。按用户任务组织页面，不机械地为每个功能建一页。沿用已有产品术语和设计资产。

输出信息架构图与核心流程图，可嵌入同一规格文档。区分用户看到的信息组织与内部软件组件；不同分类维度用视图或筛选表达，不混成同一层导航。

每条核心路径明确入口、前置条件、用户意图、操作、分支、反馈、完成状态和失败后去向，并关联需求 ID。先验证主要路径，再展开次要页面。

## 2. 从线框到可操作原型

先确定页面目的、内容层级、主次操作和信息密度，再做视觉细节。视觉设计（字体、颜色、间距、组件、无障碍、响应式）优先交给宿主已装的界面设计技能（如 impeccable）；没有时沿用项目已有设计资产，按实际需要确定。不机械套用仪表盘风格。

交互应明确“初始状态 → 用户动作 → 系统反馈 → 新状态”。覆盖适用的加载、成功、空数据、错误、禁用、无权限、离线和部分完成状态；常规细节自主决定，重大体验取舍提供可比较方案。

需要验证导航、表单或任务流程时，制作实际可操作原型。复用目标环境已有工具和组件，只加入必要依赖；提供入口或启动方法。将模拟数据与页面逻辑适当分离，并在原型及说明中标明哪些是真实交互、模拟服务、占位数据、尚未实现功能。

原型响应点击不能证明后台已实现。工具确实无法产出所需原型时，提供线框与交互规格作为阶段产物，明确“可交互原型未完成”，不得等同通过原定验收。

## 3. 真实走查与反馈

实际操作原型，检查核心任务、返回路径、数据变化和关键异常反馈；按目标设备检查布局、可读性及适用的键盘操作。记录路径、操作、期望、结果与证据。没有运行只能标记规格审查，不能写原型验证通过；用户未评价也不能冒称用户验收。

发现问题后按以下边界处理：

| 问题 | 处理 |
|---|---|
| 已定需求下的常规交互细节 | 本角色完善并记录 |
| 缺少产品行为或需求互相矛盾 | 提出需求变更，经主对话送需求角色 |
| 本地/云端、实时性、后台状态等机制影响体验 | 与架构角色分析约束，再协调必要的 PRD 修改 |
| 价值、范围或优先级改变 | 主对话组织用户决策 |

不要因实现方便擅改体验，也不要让原型提前锁定数据库、服务或技术栈。

## 4. 交付

维护 `PROTOTYPE.md` 与原型文件：规格、信息架构、用户流程、状态、视觉约定、模拟边界、验证结果放在同一文档的对应章节。复杂流程需要拆文件时只保留引用。

通过共享交接记录向架构提供版本、需求和页面 ID、需持久化的数据、用户可见状态、权限归属、同步时效、外部服务预期、未决问题及原型入口。描述预期效果，不指定实现机制。用户认可核心路径后形成体验基线；次要未决项须标清影响，供总控判断能否继续。
