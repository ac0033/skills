# 共享协议

四个技能共用本文件，只规定设计阶段的协作；贯穿全程的规则以项目 AGENTS.md 工程流程块的 R1–R10 为准，这里只引用编号。项目里还没有该规则块（未装套件、套件版本较旧或项目用自有闸门）时，读 `../../engineering-kit/kit/rules/AGENTS.block.md` 取得各条内容。项目事实留在项目目录；不要把某个项目的需求、凭据或进度写入技能。优先级按 R1（宿主规则与用户的全局规则同级），本协议不授予额外发布、付费、外发或系统修改权限。

## 1. 决策与用户参与

AI 主动分析、拆解、比较、推荐和核验。用户决定产品目标、范围、优先级，以及影响隐私、数据控制、成本和核心体验的取舍。普通技术细节由 AI 自主处理；重要决定用“问题与具体场景 → 可行选项及影响 → 推荐及依据 → 用户待决定项”表达，不把技术工作转交给用户。

提问与授权按 R2、R3。用户确认应针对具体可审成果，而不是要求用户批准空白方案。

将信息来源区分为用户陈述、可核验证据、AI 分析和假设（R5）；不虚构研究、市场、技术能力、执行结果或费用。

## 2. 唯一归属与精简目录

新项目第一步先装 engineering-kit（见总控第 1 节），文件放它建好的阶段目录和记录目录（R6）；项目已有等价目录时沿用（旧版套件装的项目按其配置里的阶段目录对应放置，并按同步时的升级提示补上总览目录和 `review` 状态值）：

| 文件/位置 | 唯一内容 | 负责人 |
|---|---|---|
| `docs/00-总览/PROJECT_STATE.md` | 当前阶段、产物版本与有效性、待决/阻塞和下一动作的索引 | 总控 |
| `docs/00-总览/RECORDS.md` | 重要探索发现、非技术决策、按授权采用推荐的决定、跨阶段变更和增量交接，按记录 ID 引用 | 总控汇总，各角色交回记录 |
| `docs/01-需求/PRD.md` | 产品问题、需求、规则、范围和验收条件 | 需求 |
| `docs/02-原型/PROTOTYPE.md`、`docs/02-原型/prototype/` | 信息架构、用户流程、交互规格、原型文件与走查结果 | 原型 |
| `docs/03-架构/ARCHITECTURE.md`、按需 `docs/adr/` | 架构图、机制、技术决定与评审；重大决定单独 ADR（只追加的记录） | 架构 |
| `docs/00-总览/IMPLEMENTATION.md` | 实施交接、准备度、追踪矩阵（只引用任务 ID；任务切片在 `docs/04-开发/` 的计划里） | 架构建立，交接后 Coding Agent 维护 |

`PROJECT_STATE.md` 只做索引，不复制决策全文。需求说明只在 PRD；原型、架构通过 ID 引用。ADR 已记录的理由只在其他文件放链接。探索、变更和交接统一记录在 `RECORDS.md`，专业评审记录在对应规格文档；内容复杂到确需独立维护时再拆，拆后删除重复正文并保留引用。

同一时间每份权威文件只有一名写入者。子角色提出上游变更，由总控交给该文件负责人；总控也不能用汇总覆盖专业结论。多工作树时先核对基准再合并，完成合并后才更新项目状态；仅接到“已完成”消息不等于文件已合入。

被委派的子代理只读 `PROJECT_STATE.md` 和 `RECORDS.md`，将待登记内容随结果交回总控，不直接创建、追加或另建替代记录文件。子技能未经总控被直接加载时，当前主对话先加载总控并兼任记录负责人，不与其他上下文同时写入。

## 3. ID、版本与状态

有现成 ID 则沿用；否则按需采用下表，不给每个小细节编号。ID 稳定，改名不换 ID，已删除 ID 不复用。

| 类别 | 前缀 |
|---|---|
| 目标与需求 | `GOAL`、`FR` 功能、`NFR` 质量、`BR` 业务规则 |
| 体验 | `UJ` 用户旅程、`PAGE` 页面、必要时 `INT` 交互 |
| 技术与实施 | `COMP` 组件、`ADR` 决策、`TASK` 任务、`TEST` 测试 |
| 协调记录 | `REC`，同一记录可关联发现、决定、变更与交接 |

例如 `FR-001`。每份主要产物声明版本、更新时间、负责人和所依据的上游版本。可使用简单递增修订号或既有版本规则；版本号本身不表示已确认。

不同维度分开存，不把“已确认、已实现、已验证”混成单一状态：

| 维度 | 值 |
|---|---|
| 决策 | 建议、暂定、已确认、按授权采用推荐（R2）、暂缓、否决、已取代；确认附来源 |
| 文档 | 写在文件头 `状态：`，取值按 R5：draft（草稿）、review（评审中）、active（基线）、superseded（已取代） |
| 对上游有效性 | 当前、待复核；注明所依据版本 |
| 实施 | 未开始、进行中、已实现 |
| 验证 | 未验证、通过、失败、阻塞、不适用（须理由） |

文件头只写文档状态，其余维度写在 `PROJECT_STATE.md` 和追踪矩阵。一个文档可以同时是“active、待复核”。用户确认、工程检查、交互走查、真实服务验证和发布分别报告（R5）。

## 4. 变更与增量交接

发现变化后：

1. 记录来源、原行为、新发现及理由，引用受影响 ID。
2. 识别产品、交互、架构、任务和测试的影响，仅将相关下游标为待复核。
3. 属于已有授权的常规修正直接推进；重大新取舍交用户决定（用户已授权按推荐执行时按 R2 取推荐并记录），其他独立工作继续。
4. 由所属角色修改产物并更新版本，补做受影响检查。
5. 总控核对交回文件，更新引用和状态，记录接收结果；未经复核不得恢复为当前。

交接记录仅含：发送方/接收方，文件路径及版本，新增决定或发现，受影响 ID，所需动作，阻塞与可继续范围，用户确认依据，接收状态。复用 `REC`，不复制上游全文。聊天中的新决定未落盘时先核对并同步，不因文档旧就忽略用户的最新明确指令。

跨阶段冲突由总控组织处理，不能以谁回复更晚来裁决。同步只覆盖真实受影响的角色，不每次通知全部角色。

## 5. 续接与完成边界

新上下文先读状态索引，再打开所需产物及确认来源；核对版本和实际文件。索引与产物不一致时先修复记录，不能凭聊天记忆宣布完成。

验证证据应能定位操作、版本、结果和限制；没有执行权限或工具时标为未执行/阻塞。任何阶段缺少核心条件都不能因文档存在而通过，但可以明确列出不受影响的可继续任务。

设计目标到实施交接为止；生产实施、外部服务实测和发布以用户实际任务为准。不要把设计技能调用理解为无限费用或发布授权，也不要因缺少后续发布授权而阻止当前设计工作。
