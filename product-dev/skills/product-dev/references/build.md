# 逐片开发：最小改动规则

交付段“逐片开发”和修 bug 路线“最小修复”的做法。目标是用最少的新代码把整件事做完：不写的代码不用读、不用测、不会坏。

与项目规则冲突时按 R1：闸门要求的注释和测试优先于“少写”，见下面的“闸门优先”。

## 1. 动手之前

读任务和它涉及的代码。列出这次改动必须到达的每一处：调用方、测试、测试数据、配置、导出。再看它可能弄坏什么：会销毁或暴露的数据、会失效的调用方。这些是范围；额外的功能不是。

## 2. 选最小而完整的做法

按顺序看，取第一个能完整解决问题的：

1. 需要存在吗？没人要求的功能、选项、灵活性不做，用一句话写进汇报。要求含糊时，做能完成核心任务的最小版本。
2. 代码库里已经有了（工具函数、组件、服务、模式）？照周围代码的用法用它。
3. 标准库或平台自带？用它；项目有自己的一套时用项目的。
4. 已安装的依赖能做？用它。不为几行代码新增依赖。
5. 能写成读者一眼看懂的一行？写一行。
6. 都不行：写刚好够用的代码。

- 对做法偷懒，对改动本身不偷懒：任务需要的每一部分都做完，包括被这次改动影响到的调用方、测试和测试数据。
- 没人要求的抽象、包装、类型转换、选项、配置、样板和“以后可能用到”的代码不写。第三处用到之前不抽公共代码；一次性的操作不新建工具文件。
- 删除优于新增。沿用代码库已有的结构：分层、接口和约定。
- 弄清必须改到哪些地方之后，能工作的最短改动胜出。需要破解才能看懂的一行不算短。
- 移动或合并的代码保留原有的错误处理和校验。
- 大小相当的做法里，选在边界情况下也正确的那个。
- 有已知限制的捷径留一行注释，格式 `shortcut: <限制>, <什么时候该升级>`，方便以后全仓检索。

不能省的：信任边界上的校验、防止数据丢失的错误处理、安全、无障碍、真实硬件需要的校准、用户明确要求的任何东西。

## 3. 闸门优先

外部做法主张少写注释、琐碎改动不写测试；本插件的项目以闸门为准（R1）：

- 注释：每个源文件开头的业务职责说明、导出项前的说明照写。除此之外，只注释代码表达不出来的“为什么”，一行为限。
- 测试：改源文件就要有引用它的测试，并随改动一起改。确实没有可测行为的（只有类型、只做再导出），在豁免表里写理由，不绕过闸门。
- 闸门不过就改代码或补测试，变绿的办法按 R4。

## 4. 每一片的循环

写测试 → 实现 → 验证 → 提交 → 下一片。

- 一次只改一件事。新增组件、重构旧代码、改构建配置是三次提交。重构和新功能分开。
- 写了约一百行还没跑过测试，就停下来先跑。
- 片与片之间不留坏状态：能构建，已有测试通过。
- 没做完但要先合并的功能，用开关挡住，默认关闭；新增的选项默认取保守值。
- 每片能单独回退：新增优于修改；数据迁移带回退脚本；不在同一次提交里既删旧的又换新的。
- 同一条验证命令通过之后，代码没变就不重复跑。
- 只动任务范围内的文件。范围外看到值得改的（多余的导入、可以更好的报错），记下来写进汇报的“后续待办”，不动手；看不懂的注释不删。

每片做完自问：

1. 这片只做了一件事，并且做完整了吗？
2. 能不能用更少的代码做到？有没有为还不存在的需求写的东西？
3. 相关测试、构建、类型检查、静态检查都过了吗？
4. 提交说明写清了改了什么、为什么吗？

## 5. 修 bug 时

- 改之前先搜被改函数的全部调用方，再在共用代码里把根因修一次；不在某一个调用方里绕过去。
- 只改让失败测试转绿所需的代码，不顺手重构。
- 修完回到修 bug 路线的“查同类与调用方”，逐个确认调用方。

## 6. 汇报

跳过了什么、没检查什么、用户必须知道的风险，写进四段汇报的“用户需知”，不另起格式。
