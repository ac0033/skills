# 任务拆解

交付段第一步“任务拆解”的方法。计划写在 `docs/04-开发/` 下，用 `docs/_templates/plan.md`；任务 ID 在这里产生，追踪矩阵只引用它。逐片怎么做见 [build.md](build.md)。

单文件、范围一目了然的改动不用拆（走小改动路线）；实施交接里已经有定义清楚的任务时，直接沿用，只补缺的栏。

## 1. 先读后拆

拆解期间只读不写代码。读功能契约（或实施交接）、相关模块和已有的同类实现，记下三件事：沿用哪些现成的模式，组件之间谁依赖谁，哪里有风险或还不清楚。还不清楚的先回去澄清，不带进计划。

项目里已有未完成的计划时：同一件事的修订，原地更新；另一件事，新建一份计划文件，不覆盖、不改名、不删除原来那份，它可能正在另一个会话里执行。两件事看起来冲突、分不清是不是同一件事时，停下问用户。

## 2. 画依赖图

把要动的部分按依赖关系排出来，例如：

```
数据结构
  ├─ 接口的类型与校验
  │    └─ 接口
  │         └─ 前端调用层 → 界面
  └─ 迁移与初始数据
```

被依赖的先做。两部分共用一个接口约定时，先把约定定下来，两边才能各自推进。

## 3. 切成纵向切片

一片是一条能从头走到尾的功能路径，做完就能验证。不按层切。

| 切法 | 例子 | 说明 |
|---|---|---|
| 横向（不用） | 先建全部表，再写全部接口，再做全部页面，最后联调 | 到最后才知道能不能跑通 |
| 纵向（默认） | “能注册”→“能登录”→“能创建条目”→“能看列表”，每片含自己的表、接口、界面 | 每片都交付能用、能测的功能 |
| 约定先行 | 第 0 片只定接口约定；随后后端按约定实现，前端按约定用模拟数据；最后一片联调 | 用于两端并行 |
| 风险先行 | 最没把握的一片排第一，例如先证明长连接能通 | 失败得早，损失小 |

## 4. 任务大小

| 大小 | 涉及文件 | 范围 | 处理 |
|---|---|---|---|
| 特小 | 1 | 一个函数或一项配置 | 可与相邻任务合并 |
| 小 | 1–2 | 一个组件或一个接口 | 合适 |
| 中 | 3–5 | 一条功能路径 | 合适 |
| 大 | 5–8 | 跨多个组件 | 再拆 |
| 特大 | 8 以上 | — | 必须再拆 |

出现下面任一情况也要再拆：一次专注的会话做不完；验收条件三条写不完；同时动两个互不相干的子系统；任务标题里要用“和”连接两件事。

## 5. 写任务

计划模板的“任务切片”表每行一个任务，各栏的要求：

| 栏 | 要求 |
|---|---|
| 任务 ID | `TASK-序号`，全计划唯一 |
| 内容 | 一句话说明这片交付什么能力；预计要动的文件写在后面 |
| 依赖 | 依赖的任务 ID，没有写“无” |
| 验收条件 | 具体、可检验，不超过三条；来自契约的验收标准，不弱化 |
| 验证方法 | 跑哪条测试命令、构建命令，或手工检查什么 |
| 状态 | 未开始、进行中、已实现 |

没有验收条件、只写“实现某功能”的任务不算拆完。

## 6. 排序与检查点

排序满足四条：依赖在前；每做完一片系统仍能构建、已有测试仍通过；高风险的靠前；每两三片设一个检查点。

检查点写在计划模板的“检查点”一节，内容固定为：全部测试通过、能构建、核心路径能从头走到尾。检查点属于重复性工作，按 R10 攒到整块时段跑；需要用户看过才能继续的检查点事先写明。

哪些可以并行：互不依赖的切片、给已实现功能补测试、文档。哪些必须串行：数据库迁移、共享状态的改动、有依赖链的任务。共用接口约定的两部分先定约定再并行。并行派发子代理时按 R9 划清各自的文件范围。

计划里另写两节：风险与应对（风险、影响大小、怎样应对）；待用户决定的问题。

## 7. 开工前核对

- 每个任务都有验收条件和验证方法。
- 依赖关系已标出，顺序正确。
- 没有任务超过约五个文件。
- 阶段之间有检查点。
- 没有覆盖别人未完成的计划。
- 中高风险的计划已给用户看过（或有 R2 的授权记录）。

出现下面的情况说明拆得不对：没有写下任务清单就开始实现；任务全是特大；计划里没有验证步骤；没有考虑依赖顺序。
