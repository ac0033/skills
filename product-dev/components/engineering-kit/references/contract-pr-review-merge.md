# 功能契约：PR 双审与合并入口

状态：done（用户 2026-11-10 确认范围与全部口径；2026-11-10 在 0.3.0 实现。验收标准 1–10 由套件测试覆盖并通过：第 1 条为现有测试，第 2–10 条见 `kit/tests/pr-flow.test.mjs`。真实 GitHub 仓库验证：用户 2026-11-10 报告已测试通过）

## 目标与范围

让套件能证明：某个 PR 合并时，CI 已对它的最终提交全部通过，且代码复审和一致性审都是针对这个最终提交做的。

范围内：

1. **流程开关。** 配置新增 `modules.gate.reviewFlow`，取值 `pre-push`（现有流程）或 `pr`（新流程）。两种流程并存。
2. **推送核对（`verify.mjs`）。** `pr` 流程下只要求静态检查和与当前代码一致的通过测试记录，不再要求复审记录。`pre-push` 流程行为不变。
3. **复审登记（`review.mjs`）。** `pr` 流程下新增 `--pr <编号>` 与 `--kind code|consistency`。登记时用 `gh pr view` 读取 PR 状态、最终提交和检查结果；PR 未打开或 CI 未全部通过时拒绝登记。记录写入 git 公共目录的 `engineering-gate/pr/<编号>/<kind>.json`，包含结论、复审者、最终提交、报告副本路径和时间。
4. **合并入口（新脚本 `merge.mjs <PR>`）。** 依次核对：PR 处于打开状态；CI 对当前最终提交全部通过；要求的每种审查都有 pass 记录，且记录里的提交等于当前最终提交。全部满足才执行 `gh pr merge --match-head-commit <提交>`。全部文件在 `reviewIgnore` 之内的 PR 只核对 PR 打开与 CI。任何一项不满足就列出原因并以 1 退出，不合并。
5. **钩子提示。** `pre-bash.mjs` 继续拒绝直接 `gh pr merge`，拒绝信息改为指向 `merge.mjs`。
6. **文档。** 更新 `SKILL.md` 第 5 节、`process.md` 第 4 节和 `AGENTS.block.md` 的第 4–6 条，使文字与实现一致。版本升为 0.3.0。

范围外：

- 受影响测试选择。推送前仍跑配置的 `testCommand` 全量。
- 证明复审者确实是独立子代理。复审者名字仍由登记者填写。
- GitHub 以外的平台。没有 GitHub 远程或没有 `gh` 的项目继续用 `pre-push` 流程。
- “同一 PR 三轮审查后须交用户决定”（`process.md` 第 4 节第 4 条）的自动计数。

## 怎样证明正确（验收标准）

`gh` 的调用通过可注入的函数完成（做法同 `release.mjs` 的 `testRunner`），测试用假的 `gh` 输出，不访问网络。每条对应至少一个测试：

1. `pre-push` 流程：现有 112 个测试全部通过，行为无变化。
2. `pr` 流程推送：有通过的测试记录、没有复审记录时，推送核对通过。
3. 登记复审：CI 有任一检查未通过或仍在运行时，拒绝登记。
4. 登记复审：PR 已关闭或已合并时，拒绝登记。
5. 合并：两种审查都 pass 且提交一致、CI 全过时，调用合并命令，并带上 `--match-head-commit`。
6. 合并：复审之后 PR 又有新提交（最终提交变化）时拒绝，并指出哪份记录过期。
7. 合并：缺少任一要求的审查记录，或其中一份结论为 fail 时拒绝。
8. 合并：CI 在当前最终提交上未全过时拒绝。
9. `gh` 不存在或调用失败时，登记与合并都报错退出，不放行。
10. 配置为 `pr` 流程的项目，同步后的冒烟测试通过；从 0.3.0 回滚到 0.2.x 后旧流程可用。

另需一次真实验证：在一个带 CI 的 GitHub 测试仓库里走完“推送 → CI → 两次登记 → 合并”，并验证“登记后追加提交则合并被拒”。

## 风险级别与回滚方案

风险：高。改动闸门语义，新增合并通道，依赖外部命令 `gh`。

- 新流程由配置开关启用，默认值见下方已确认的口径；未启用的项目不受影响。
- 出问题时把 `reviewFlow` 改回 `pre-push` 即恢复旧流程，不需要回滚套件。
- 套件本身可用 `sync.mjs --from-tag engineering-kit-v0.2.x` 回滚。
- 实现须排在审计修复（1–16）合并之后，两者改动同一批文件。

## 已确认的口径

以下五条均已由用户确认（2026-11-10），按此实现：

1. **默认流程。** 默认 `pre-push`，项目自行改为 `pr`。这样升级套件不会改变已安装项目的行为。
2. **“CI 全部通过”的定义。** PR 上报告的每一项检查都是成功、跳过或中性；一项检查都没有时视为未通过。没有 CI 的项目应留在 `pre-push` 流程。
3. **低风险 PR 的一致性审。** `process.md` 第 4 节的分档允许低风险改动把一致性审延期，合并入口须与之一致：代码复审必需（只改文档的 PR 不审，见范围第 4 项）；一致性审要么有 pass 记录，要么有一条写明理由的延期记录（`review.mjs defer --pr <编号> --kind consistency --reason "<理由>"`），延期记录也绑定最终提交。
4. **合并方式与分支清理。** 默认 squash 合并并删除远端分支，可用 `--method` 改合并方式。
5. **记录位置。** PR 记录放 git 公共目录（所有工作树共用），因为复审和合并可能在不同工作树里进行。测试记录按审计修复第 6 条改为每个工作树各自一份，两者不冲突。
