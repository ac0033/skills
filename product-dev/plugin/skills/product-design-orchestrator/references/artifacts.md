# 按需产物模板

本文件规定字段和最小内容，不要求照抄所有标题。只读取当前阶段的章节；已有等价文档继续使用。模板是结构，不是完成证据。各文件的共享头部为：名称、版本、`状态：`（文档状态，取值见共享协议第 3 节）、负责人、更新时间、上游文件及版本；规则见[共享协议](shared-protocol.md)。

## 1. 项目状态与记录

### PROJECT_STATE.md

```markdown
# 项目状态
项目：……；设计目录：……；当前阶段：……；更新时间：……

## 产物索引
| 产物路径 | 负责人/上下文 ID | 版本 | 文档状态 | 上游版本 | 有效性 | 确认/证据引用 |
|---|---|---|---|---|---|---|

## 待处理
| 问题或动作 | 负责人 | 依赖 | 阻塞范围 | 对应记录 | 下一步 |
|---|---|---|---|---|---|

## 阶段结论
已满足条件：……；未满足条件：……；可继续范围：……
```

### RECORDS.md

每条重要记录采用下列字段；无关字段省略。用户决定、发现、变更与交接属于同一事项时合并记录，状态表只引用记录 ID。

```markdown
## REC-001：事项名称
- 来源/日期：……
- 背景与证据：……
- 备选与建议：……
- 决策状态/确认依据：……
- 变更：原内容 → 新内容；理由……
- 影响：需求/页面/组件/任务/测试 ID……
- 交接：发送方 → 接收方；产物路径@版本……
- 下一动作/阻塞/可继续范围：……
- 接收与核验结果：……
```

<a id="prd"></a>
## 2. PRD.md

| 板块 | 内容 |
|---|---|
| 产品定义 | 背景与问题、用户、现有做法及不足、核心价值、目标与测量方式 |
| 范围与场景 | 长期愿景、本期范围、MVP 的价值验证目标、不做事项；主要场景和优先级理由 |
| 需求与规则 | 按功能域组织需求；质量要求、业务规则、角色权限、数据归属和外部约束 |
| 验收与不确定性 | 核心路径验收、假设和证据、风险、待确认问题、确认记录引用 |

每个需求最少包括：ID、名称、目标/场景引用、用户价值、优先级、依赖、预期行为、验收标准和决策状态。验收使用“给定条件—操作/触发—可观察结果”；有指标则记录依据，没有依据不填确定数值。

需求级旅程描述任务和预期结果，不规定页面布局。正文只记录当前有效需求，探索过程引用 `RECORDS.md`。

## 3. PROTOTYPE.md

| 板块 | 内容 |
|---|---|
| 入口与范围 | 原型入口/启动方法、适用设备、对应 PRD、覆盖与未覆盖范围 |
| 信息架构与旅程 | 导航/页面层级图；主要旅程及流程图、需求引用 |
| 页面与交互 | 页面 ID/目的/主要信息/主次操作；交互状态、用户反馈、异常与恢复 |
| 视觉与实现边界 | 沿用的设计资产、组件约定、响应式及无障碍；真实、模拟、占位和未实现内容 |
| 验证与反馈 | 实际操作结果、需求缺口、架构问题、用户确认及可交接范围 |

原型走查记录：`需求/路径 ID | 前置条件 | 操作 | 期望 | 实际结果 | 验证状态 | 证据/版本`。

架构需要的交接信息：哪些数据需保存、谁可读写、用户可见状态、后台任务与同步时效、外部服务依赖、已验证体验和未决问题；使用协调记录引用这些章节。

<a id="architecture"></a>
## 4. ARCHITECTURE.md 与 ADR

| 板块 | 内容 |
|---|---|
| 目标与全貌 | 架构摘要、关键需求与约束、系统上下文图、高层系统架构图 |
| 组件与运行 | 组件职责表、依赖/数据归属、重要正常及失败路径、关键机制 |
| 选型与部署 | 技术选择依据、兼容条件、部署单元/环境/网络/配置、运维与成本；重大理由引用 ADR |
| 评审与演化 | 需求覆盖、风险与验证证据、未验证假设、必要实验、可预期扩展点及迁移条件 |

组件表：`组件 ID | 职责与不负责事项 | 输入/输出 | 数据/状态归属 | 依赖 | 需求依据`。

评审记录：`问题 | 严重程度 | 相关需求/组件 | 依据 | 修复/验证方法 | 负责人 | 状态`。重大问题需注明阻塞全部还是局部任务。将场景推演与运行实测分开记录。

重大决策按项目的 `docs/_templates/adr.md` 写成 `docs/adr/ADR-编号-名称.md`。ADR 是只追加的记录（R6）：决定确认后才建文件，尚未确认的备选留在 `ARCHITECTURE.md`；按授权采用推荐（R2）的技术决定先写在 `ARCHITECTURE.md` 并登记到 `RECORDS.md`，用户确认或收尾时未被推翻后再建 ADR；取代旧决定时新建 ADR，在“关联”里写明被取代的编号，旧文件不改。

<a id="implementation"></a>
## 5. IMPLEMENTATION.md

### 实施交接

记录产品与技术文档的有效路径和版本、目标范围、必须保持的边界、接口/数据/状态/权限契约引用、配置与环境要求、外部集成条件。密钥只写配置名称及获取责任人，不写值。

实施顺序依据能力之间的依赖、风险和可验证价值安排（任务切片由开发阶段在 `docs/04-开发/` 的计划里拆）：优先验证会推翻方案的关键假设，再完成贯通核心路径，随后完善其他本期要求。明确可独立执行的范围及统一集成点；设计不能直接替代工程实现。

### 追踪矩阵

```markdown
| 需求/目标 | 原型引用 | 架构引用 | 实施顺序项（开发阶段补任务 ID） | 实施状态/代码引用 | 验收或测试引用 | 验证状态 | 证据及限制 |
|---|---|---|---|---|---|---|---|
```

一行对应有意义的需求或能力，不对应每个函数。矩阵引用正文，不重复需求说明或全部任务细节。尚未生成的代码、测试、证据填写未产生；不适用需解释。交接后由 Coding Agent 随实现与验证更新，变更则重新检查关联项。

### 实施准备度

按范围逐项核验，给出文件与证据引用：

1. 本期产品范围、核心需求与验收标准已明确确认。
2. 关键体验有足够证据；相应架构组件和机制能够支撑。
3. 所需接口、数据、状态、权限与外部依赖足以实施，无关键行为靠猜。
4. 技术、环境、配置及运维约束明确；必要凭据和授权缺口已定位到具体的实施顺序项。
5. 高风险假设已验证，或已将依赖它的实施顺序项列为不可开始；测试与最终使用路径验收有明确方法。
6. 本期功能、质量要求和业务规则在实施顺序里均有对应项和验证方法；版本一致，无未解释的多余组件。

结论与依据写在同一处：

- `READY`：当前实施范围的关键输入齐备，无阻塞问题，足以开始实施；不表示产品已完成或可发布。
- `READY_WITH_LIMITATIONS`：可以开始明确列出的独立范围；逐项列出不能开始的范围、缺口、负责人和解除条件。
- `BLOCKED`：缺少决定核心方向、边界或安全实现的关键输入，当前实施范围没有可安全开始的部分；说明需要谁提供什么。

设计批准不代替操作授权。若用户要求最终生产使用，实施阶段还必须完成必要真实接入、用户路径与部署验收；不得以原型验证或文档准备度代替。
