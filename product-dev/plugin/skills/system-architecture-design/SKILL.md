# 系统架构设计

本技能由[产品设计总控](../product-design-orchestrator/SKILL.md)加载；被直接加载时，先加载总控，由它决定只启动架构角色还是走完整流程。

主动承担架构师的技术分析，让用户理解重要取舍。先读[共享协议](../product-design-orchestrator/references/shared-protocol.md)、项目状态、PRD、原型及现有代码和部署资料；文档、ADR 与交接采用[产物模板](../product-design-orchestrator/references/artifacts.md)。

## 1. 先确定问题和边界

提取功能、质量要求、既有环境、隐私与数据归属、外部依赖及费用约束；区分已确认、建议、假设和未知。架构取决于这些要求，不先选技术再找理由。

识别用户、系统责任、外部服务、跨界数据、认证授权及信任边界。再按业务能力、处理流程、变化原因或隔离需求拆分组件；分层只是可选组织方式，不是所有系统的必选结构。

每个主要组件说明职责、边界、输入输出、依赖、数据与状态归属、失败影响和对应需求。每个组件都需有业务或必要技术依据，不为图形整齐增加模块。

## 2. 总体方案与关键机制

先提出能满足已确认需求的最简单方案。仅对有实质取舍的决定比较备选，说明复杂度、费用、运行维护、可逆性及适用条件。微服务、队列、插件、多 Agent、分布式存储都需要具体理由；未来扩展优先保留有依据的替换边界。

把精力放在错误后难以修复、风险高或影响核心体验的机制。按需分析：

| 机制组 | 必须回答的关键问题 |
|---|---|
| 数据与状态 | 谁拥有数据和状态，如何持久化、去重、并发更新、保留与删除；重启、断点后如何恢复 |
| 执行与协作 | 计算和文件在哪，本地/云端边界，任务隔离与资源限额；同步/异步、超时、重试、幂等、取消与部分完成 |
| 安全与可靠性 | 身份、权限、密钥、租户隔离、外发与日志；依赖故障、重复执行、恢复与数据一致性 |
| 性能与成本 | 真实或明确假设的负载、延迟、吞吐、瓶颈、服务限流和成本驱动；不虚构精确数字 |
| 运维与演化 | 部署单元、环境、配置、升级回滚、备份恢复、日志指标告警；外部集成边界和必要扩展点 |

AI/Agent 系统还需明确模型调用边界、上下文和状态管理、工具权限、不可信内容与提示注入、沙箱、人工审批、用量计量和失控停止条件；普通项目不强加这些内容。

对关键机制给出具体输入、处理、输出，以及失败时用户看到什么。技术选型随后完成，核实会影响方案的版本、接口、许可证或价格；不知道的标为未核实。付费调用、真实外发或部署实验按已有授权执行，设计任务本身不扩大权限。

## 3. 两张核心图与按需细化

架构图是核心交付物。必须提供可编辑的系统上下文图与高层系统架构图，优先采用环境可渲染的 Mermaid；宿主装有图表技能（如 archify）时用它生成并校验。借鉴 C4 的不同尺度视图；它是表达方法，不是人机协作流程，不必机械画齐全部层次。

- **系统上下文图**：用户、系统、外部服务与跨边界交互，不展开内部实现。
- **高层系统架构图**：主要组件及简短职责、调用/数据/事件关系、存储、执行位置及重要权限边界，不塞入字段、函数和 API 清单。

重要连线标注含义，内部外部可区分，名称与正文一致；颜色不是唯一标识。图太复杂时拆视图，不缩成无法阅读的一大张。实际渲染检查可读性；只写出图代码时标明尚未渲染验证。

仅在有助于理解或实施时增加时序、状态、数据、部署或局部组件图。接口契约、数据模型和状态转换放在对应机制说明中，细化到实施不需重新猜测核心行为的程度。

## 4. 评审与决策记录

从反对者角度检查遗漏、重复职责、循环依赖、复杂度、数据归属和权限边界。逐项走查重要需求与用户路径，推演适用的崩溃、超时、重复请求、恶意输入、资源耗尽和部分成功情景：如何发现、影响范围、恢复方式及用户体验。

区分文档推演、实际技术实验与用户验收。高风险假设需要最小验证实验时，先明确判据、环境和停止条件；失败则调查和修正，未做不写通过。重要问题按阻塞实施、阻塞局部功能、实施前需处理、可后续优化分级。

重大决定在确认后写 ADR，保留背景、备选、理由、代价、相关需求及验证依据；取代旧决定时新建 ADR 并写明被取代的编号，旧文件不改。常规细节留在正文，不创建大量 ADR。

发现产品行为或体验冲突时，说明具体需求/页面、约束、用户影响、替代方案与推荐，通过总控交给原角色处理，不自行降低产品目标。

## 5. 实施交接

维护 `ARCHITECTURE.md`，含两张核心图、机制、技术选择和评审结果。向 Coding Agent 交付[实施计划与追踪矩阵](../product-design-orchestrator/references/artifacts.md#implementation)：有效输入版本、边界和契约、实施顺序、早期风险实验、测试与真实验收方法、配置及未决项。任务切片由开发阶段在 `docs/04-开发/` 的计划里拆，矩阵只引用任务 ID。

追踪维持在需求或重要能力粒度：`目标 → 需求 → 原型 → 组件/机制 → 实施顺序项（开发阶段补任务 ID） → 测试 → 证据`。覆盖本期功能、质量要求与业务规则；无界面要求注明原型不适用及理由。代码与测试尚未产生时明确未实现、未验证，不填虚构路径。

架构设计完成和实施准备完成分别评估；准备度使用共享模板中的统一判据。用户确认总体设计后交回总控，后续工程实现另按任务范围推进。
