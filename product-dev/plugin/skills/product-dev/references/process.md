# 流程细则

入口技能各步骤的操作细则，按需读对应的节。贯穿全程的规则只写在工程流程规则块里（R1–R10），本文只写各步怎么做，引用编号，不复述。能用脚本或钩子强制的，就不靠自觉。

本文由工程套件的流程文档重组而来，按入口的步骤排列；经入口走流程时读本文。两者说法不同时，以项目自己的规则和闸门的实际判定为准（R1），并把不同之处报告出来。

命令里的 `<项目>` 指项目根目录；套件的闸门脚本装在 `<项目>/scripts/engineering/gate/` 下。套件的安装、升级、漂移检查、回滚、变更集与发布的命令只写在内部技能 [engineering-kit](../../engineering-kit/SKILL.md) 的第 1 到 4 节；其中回滚、变更集与发布要在套件源仓库的检出里做，见入口第 7 节。

## 授权边界

授权按 R2 和项目 AGENTS.md 的授权表：授权表里写了的按表执行，没写的先问用户。任务获得批准之后，推送功能分支、合并（经合并入口）、构建、预发部署属于常规动作，不必逐次再问；R2 列为始终单独授权的事项不在其内。整包发布（套件自身的发布）只提交套件目录，不推送，不开 PR，除非用户明确要求。

## 开工

对应入口的“开工检查”，所有要改文件的路线都先做。

1. 从最新主干新建分支。主干没有远程时，以本地主干为准。
2. 列出分支与工作树（`git branch`、`git worktree list`），确认没有遗留的未提交改动。遗留的先提交、归档或清理，再开新任务；不属于本任务的遗留工作按 R8 先问用户。
3. 读项目 AGENTS.md 的流程地图与目录地图；项目另有专用流程文档的一并读，按 R1 它优先于本文。
4. 按下面的“执行位置与排程”定好本任务在哪里做、先做哪项。

### 执行位置与排程

R10 的展开。目的：用户在场的时间和本机的资源，留给需要用户参与、需要判断的工作；不需要人参与的重复性工作不占用这段时间，也尽量不占用本机。

前提：排程只决定同一流程里各项工作在哪里做、先做哪项，不改变流程本身。各步骤、先后顺序、检查范围和通过标准一项不省、一项不降；排程与流程冲突时按流程办。不为了方便调度而跳过、缩小、推迟到合并之后，或用较弱的检查代替。

| 类别 | 包括 | 排在什么时候 |
|---|---|---|
| 创造性工作 | 需求澄清、方案、编码、处理复审意见、修复失败、需要用户决定的事 | 优先完成，排在用户在场的时段 |
| 重复性工作 | 全量测试、回归、端到端、构建、巡检、批量机械改动、跑闸门 | 攒成整块，在用户这一阶段要做的事做完、可以去忙别的之后一次跑完 |

“整块时段”是相对的，不指固定的钟点：凡是需要用户参与的事已经做完、用户可以离开的那一段就是，白天、夜间都可以。一个任务可以分成几轮：创造 → 重复 → 再创造 → 再重复。每一轮先把需要用户的部分集中做完，再把这一轮的重复性工作集中跑完，下一轮的创造性工作以上一轮的结果为依据。

- 执行位置：开发和测试凡是能在云端会话执行的，都放到云端。云端不占本机资源，本机休眠时照常运行。
- 能放云端的条件：代码已推送到远程；不依赖只在本机才有的东西（未推送的文件、本机的数据库或服务、本机凭据、图形界面、硬件）。不满足条件的才留在本机，并在汇报里说明原因。
- 开工时定顺序：列出本任务的创造性部分和重复性部分。先做完创造性部分并提交快照；重复性部分排队，不穿插在中间打断。互不依赖的重复性任务合成一批。
- 用户在场时，本机只跑小范围的快速检查（与改动直接相关的单元测试、静态检查），供写代码时即时反馈。全量和耗时的检查放云端，或留到整块时段。
- 与闸门的关系：推送仍须有与当前代码一致的通过测试记录，复审、CI 与合并的先后照“测试、审查与合并”一节，都不因排程而改变。在云端会话里开发的，闸门在云端跑、从云端推送；留在本机的，把“跑闸门、推送”放进本轮的整块时段。
- 每一轮整块跑完后集中汇报一次：通过与失败、失败的具体项、需要用户决定的事。失败不自行降低标准，修复属于创造性工作，放进下一轮用户在场的时段。
- 启动云端会话和定时任务属于有费用的外部动作，按 R2 执行。

## 需求与方案

对应入口的“澄清问题”“功能契约”“方案对比”“用户选定方案”。

- 低风险改动直接做。中高风险（跨模块、新接口、数据库结构、权限、费用、服务器配置）先澄清需求，写功能契约，取得用户确认。
- 澄清按 R3：先查已有资料和确认记录，查得到的不问；剩下的归成一张清单一次问完，每个问题给出选项，推荐项放第一并写一句理由。
- 契约放在 `docs/04-开发/`，模板是 `docs/_templates/feature-contract.md`。契约定义“怎样证明正确”，验收标准不得擅自弱化。
- 实现中自行确定的口径要单列，待用户确认，不写成已决定。
- 方案对比至少写三栏：复杂度、风险、能否回退。推荐只是建议；用户选定或“按授权采用推荐”之后才成为决定，并写进决定记录。

## 配置闸门

对应入口的“配置闸门”。架构选定技术栈之后，改项目的 `engineering.config.json`：

| 字段 | 填什么 |
|---|---|
| `modules.gate.testCommand`、`testEnv` | 本项目跑测试的命令和它需要的环境变量。Python 项目在 `testEnv` 里设 `PYTHONPATH` |
| `layout.sourceGlobs`、`testGlobs` | 源文件和测试文件的匹配规则。Python 项目把 `sourceGlobs` 改成 `**/*.py` |
| `rules.reviewIgnore` | 只应包含纯文档 |
| `modules.review.reviewers` | 加上 `product-dev:code-reviewer`，否则用它做的复审登记不了（默认名单见 [review.md](review.md) 第 1 节） |
| `modules.gate.reviewFlow` | 默认 `pre-push`；有 GitHub 远程、已登录的 `gh` 且 PR 上有 CI 检查的项目可以改成 `pr`（建议项，由用户决定或按授权采用推荐） |

同一步还要定两件事，都由用户决定：要不要建远程仓库和 CI（建远程仓库是外部动作，先得到批准；不建的话“PR 与 CI”一步做不了，要如实写未执行）；`pre-push` 流程下由谁、经哪个入口合并，定了就写进项目的 AGENTS.md。安装时没加 `--profile` 的项目没有脚手架，包清单、测试框架等按选定的技术栈自己建，默认的测试命令也要相应改掉。

配完验证闸门拦得住：临时放一个必然失败的测试，跑 `node scripts/engineering/gate/gate.mjs`，确认它报失败；撤掉这个测试再跑一次，确认通过。两次输出都留作证据。改动里有代码文件、却没有任何文件匹配 `sourceGlobs` 与 `testGlobs` 时闸门会报错，多半是这两项没按项目改。

## 开发细则

对应入口的“逐片开发”，做法见 [build.md](build.md)，这里是闸门要查的三件事：

- 测试先行：改源文件前，先写或补引用它的测试。测试随改动一起改。闸门靠“测试文件是否引用了源文件的模块名”判断，经 index 再导出的间接引用识别不出来，这种情况在豁免表里写理由。
- 注释：每个源文件有业务职责说明；导出的函数、类、常量前有说明（输入输出、异常、为什么这样做）。
- 目录：代码按语言惯例放 `src/`、`tests/`。新顶层目录须在白名单内：`layout.topLevelAllowed`，加上 `sourceGlobs`、`testGlobs` 里写明的顶层目录。

## 测试、审查与合并

对应入口的“机械闸门”“PR 与 CI”“独立复审”“合并与收工”。

目标顺序：PR 前受影响测试 → CI → 独立代码复审和一致性审 → 合并。套件闸门的 `pr` 流程实现了“CI → 双审 → 合并入口”这一段；受影响测试选择尚未实现，推送前仍跑配置的 `testCommand` 全量。默认的 `pre-push` 流程次序不同：复审在推送之前，见下面的“两种复审流程”。项目已有更完善流程时，以项目规则和实际闸门为准（R1）。

1. PR 前执行静态检查及受影响的单元、集成、端到端、视觉和安全检查；不能可靠判断影响范围时扩大范围或跑全量，说明选择及结果。测试用隔离环境和合成数据。
2. CI 对最终提交执行全量单元测试和项目适用的全量集成测试；端到端、兼容性、安全等检查按风险安排，明确跳过的理由。适用的必需检查通过后进入审查。
3. 按下方分档进行独立代码复审和增量一致性审（矛盾、重复、过时）；一致性审可以集中审多个 PR，但每个 PR 的最终提交、所做审查的结论及证据各自记录。合并前核对 PR、最终提交、CI 和该档要求的审查；提交或基线变化后重新核查受影响部分。
4. 审查发现的高、中级问题，以及影响体验或使用的问题在合并前修复；低级问题按项目规则记录并安排修复。本次引入的矛盾、重复和过时问题在本 PR 修复。同一 PR 三轮审查后仍需下一轮时，向用户说明问题、原因、已做处置和建议，等待用户决定。
5. 合并遵循项目规定与实际授权；不绕过失败的必需检查。`pr` 流程下合并只经 `merge.mjs`，它核对 CI 与两项审查都针对 PR 的最终提交；`pre-push` 流程的记录只证明推送前复审，不能证明 CI 后双审查或最终 PR 绑定。

怎样读闸门的输出：闸门通过时只打印测试结果一行，不逐项列出静态检查。测试先行或注释检查不过时，闸门先报出问题并且不跑测试，所以看到“测试通过”就表示静态检查也过了；括号里的源文件数是本次改动里被静态检查的源文件数，为 0 表示这次没有改到源文件。

### 审查分档

风险分级同“需求与方案”一节。拿不准风险档位时按高一档处理。

| 改动 | 代码复审 | 一致性审 |
|---|---|---|
| 只改文档（`reviewIgnore` 之内） | 不做 | 并入每周巡检 |
| 低风险小改动 | 每个 PR 合并前 | 可延期：并入每周巡检，或与其他 PR 集中审；延期要写明理由 |
| 中高风险 | 每个 PR 合并前 | 每个 PR 合并前 |

代码复审不攒到合并后：结论绑定 PR 的最终提交，合并后才发现的问题已在主干上，后续 PR 又叠在其上。一致性审可以集中审多个 PR，结论仍按 PR 各自记录。复审怎样派发、任务书和报告格式见 [review.md](review.md)。

### 两种复审流程

由 `engineering.config.json` 的 `modules.gate.reviewFlow` 决定，命令都在项目的 `scripts/engineering/gate/` 下。

- `pre-push`（默认）：`gate.mjs` 通过后由独立子代理复审，`review.mjs pass|fail --reviewer <名> --report <报告> --summary "<一句话>"` 登记；推送时核对静态检查、测试记录和复审记录，三者都绑定当前代码树。套件不提供合并入口，Claude Code 的钩子拒绝直接 `gh pr merge`（别的宿主里没有这层钩子，只有 git 的 pre-push 钩子生效，同样不得直接合并）；合并按项目约定的入口，并等 CI 全部通过。项目没有约定入口时由用户合并或由用户指定入口。
- `pr`：`gate.mjs` 通过后即可推送，推送核对只要求静态检查和与当前代码一致的测试记录。CI 在 PR 最终提交上全部通过（每项检查成功、跳过或中性；一项都没有视为未通过）后按上表分档审查并登记，PR 未打开或 CI 未全过时拒绝登记：
  - 代码复审：`review.mjs pass|fail --pr <编号> --kind code --reviewer <名> --report <报告> --summary "<一句话>"`。
  - 一致性审：同上，`--kind consistency`；按分档可延期时用 `review.mjs defer --pr <编号> --kind consistency --reason "<理由>"`。
  - 合并：`merge.mjs <编号> [--method squash|merge|rebase]`。PR 打开、CI 全过、代码复审为 pass、一致性审为 pass 或延期、两份记录的提交都等于当前最终提交，才执行 `gh pr merge --match-head-commit`（默认 squash 并删除远端分支）；否则逐条列出原因，不合并。PR 又有新提交时记录过期，重新审查后再登记。
  - 只改文档的 PR（全部文件在 `reviewIgnore` 之内）按上表不做审查，合并入口只核对 PR 打开与 CI 全过；PR 文件列表为空或达到 100 个（`gh` 可能截断）时按含代码处理。其余 PR 合并入口不判断风险档位：代码复审必需，能否延期一致性审由登记者按上表判断。
  - 需要 GitHub 远程和已登录的 `gh`；没有 CI 的项目留在 `pre-push`。

## 预发、生产与事故回归

对应入口的“验收与发布”“回归入库”。生产发布、回滚、数据恢复、破坏性迁移的授权按 R2。

- 预发使用与生产一致的发布产物，按风险执行核心流程、冒烟、验收、回归、视觉、兼容、安全、性能与负载检查；压力测试在专项环境按需进行。修改或修复后做针对性 sanity 检查。记录不适用项及原因。
- 发布前准备并验证回滚方案、上一版本与数据迁移的兼容性、备份和恢复路径；镜像回滚不等于数据恢复。按项目授权部署，小范围灰度和健康检查通过后扩大，生产持续监控，异常按授权和预案处置。
- 用户验收的证据写进验收证据包（模板 `docs/_templates/acceptance-pack.md`，放 `docs/acceptance/`），发布记录放 `docs/release/`。
- 事故或测试漏检须调查为何测试和 AI 审查未发现、是否缺少测试或安全检查、CI 是否需要调整。将问题转成稳定、可重复的回归用例，放入适当阶段；无法自动化时记录原因、责任人和可执行的专项检查并跟踪补齐。可将事故、相关 PR、修复和回滚整理成脱敏样例，持续评估审查能力。

## 文档与目录

位置和归属的规则是 R6，这里是它的操作细节。

| 类别 | 位置 | 怎么改 |
|---|---|---|
| 活文档（需求、架构、计划） | 阶段目录 | 原地覆盖，历史靠 git |
| 记录类（ADR、验收证据包、发布记录） | `docs/adr/`、`docs/acceptance/`、`docs/release/` | 只追加，不改旧文件（巡检会报错） |
| 模板 | `docs/_templates/` | 只读，复制后使用 |
| 阶段索引 | docs 目录下的 README | 每个阶段目录都要登记 |

- 新建文件须满足以下之一：独立生命周期、独立被引用、独立时间点。并登记到所在阶段的 README。推送核对会拦截不在允许位置、又没有理由的新文件；理由写在豁免表 `newFiles` 中。
- 项目根目录之外：须先经用户批准，不得自行创建。说明要建在哪里、建什么、为什么，得到同意后再建。会话的临时目录（scratchpad）不在此限，用完清掉。
- 项目根目录之内：可以按上面的规则创建；任务完成后逐个检查本次新建的目录和文件，不必留下的全部清理（见“收工”）。
- 大版本（例如 v2）才用新目录（如 `v2/`）；同一版本内不新建平行目录。
- 阶段目录：`00-总览`（项目状态、决定与交接记录、实施交接与追踪矩阵）、`01-需求`、`02-原型`、`03-架构`、`04-开发`、`05-测试`、`06-发布`（可在 `layout.stages` 中修改；已安装项目写在配置里的阶段不随同步改变，同步会给出升级提示）。代码仍按语言惯例放在 `src/`、`tests/`。

## 收工

对应入口的“合并与收工”，R10 的展开。

1. 合并后删除远端与本地分支，清理工作树（`git worktree remove`）。
2. 列出本次新建的目录和文件（`git status`、`git diff --name-only --diff-filter=A <基准>`），逐个检查是否符合“文档与目录”一节；不必留下的清理掉（R8）。
3. 更新阶段索引（docs 目录下的 README 和所在阶段的 README）。
4. 删除临时文件（scratchpad、导出物），不留在项目目录里。
5. 经验提炼：
   - 用户本人提出的决定或做法：直接记录到项目的 `practices/`（不跟踪）。
   - agent 总结的：只作为候选，列出标题、依据和建议归属，向用户确认后才记录或升格为能力。升格为套件能力时写成变更集，命令见 [engineering-kit](../../engineering-kit/SKILL.md) 第 4 节，走同一条原子路径。
6. 汇报分四段，各有小标题，没有内容的写“无”：任务完成情况（做了什么、是否通过、实际做了哪些检查、证据在哪里）、后续待办（谁做、依赖什么、何时做）、用户需知（已做的默认选择、已知限制、风险，以及跳过了什么、没检查什么）、经验提炼。

### 经验记录

- 记录用户本人提出或采纳、跨项目可复用的决定、规则和解决问题的方法；项目特有结论仅提炼可迁移的做法。没有可记录的经验时不强行总结。已有条目更新而不重复；未采纳的 agent 建议不作为用户经验。
- 存在用户明确授权记录且需要新建时，在项目根目录使用 `practices/`；Git 仓库把该目录加入 `git rev-parse --git-common-dir` 下的 `info/exclude`，不跟踪、不提交。非 Git 项目直接创建。
- 按主题维护 `product-development.md`、`workflow.md`、`agentic-engineering.md`，以 `README.md` 索引；按实际需要创建。
- 每条记一条可迁移的原则、适用背景、要解决的问题、具体做法、可核实的实际效果和首次出处（项目、日期、例子）。效果未确认就写明，之后在原条目更新；再次验证可补充出处。
- 本轮有新增或更新时，汇报文件和条目；没有则如实说明。

## 巡检

- 机械检查：`node <项目>/scripts/engineering/gate/hygiene.mjs`。检查顶层目录白名单、禁用文件名片段（copy、final、bak 等）、死链、阶段索引、状态合法性、记录类只追加、重复内容、空目录、超期草稿、已合并分支与残留工作树。“已合并分支”按补丁等价判断，squash 合并后的分支需人工复核。
- 上面的“阶段索引”只查各阶段目录有没有登记到 docs 根目录的 README；阶段目录里的文件有没有登记到该阶段的 README（R6），巡检不查，写完文档自己核对。
- 巡检只报告，不删除；删除按 R8。
- 套件有没有漂移不归巡检查，用 [engineering-kit](../../engineering-kit/SKILL.md) 第 2 节的漂移检查。
- 语义一致性审：由子代理只审增量（本次或本周期新增、修改的文档），找出规则与文档之间的矛盾、重复、过时；任务书见 [review.md](review.md)。
- 周期：建议每周一次，或在大批合并之后。
