# 独立复审

交付段“独立复审”一步的方法：怎样派发、审什么、怎样分级、报告怎样写才能登记。作者自查不在这里，见 [self-review.md](self-review.md)。

## 1. 派发

复审者必须是独立上下文的子代理，不是写代码的主对话自己。登记时 `--reviewer` 填实际派发的子代理名，它要在项目配置 `modules.review.reviewers` 的名单内（套件默认名单是 `feature-dev:code-reviewer`、`/code-review`、`general-purpose`）。

| 复审者（登记名） | 用在哪里 | 注意 |
|---|---|---|
| `product-dev:code-reviewer` | 首选的代码复审，定义在插件的 [agents/code-reviewer.md](../../../agents/code-reviewer.md) | 新项目在“配置闸门”一步已把它加进名单；老项目没加时见下一段。它只有只读工具，不能写文件、不能运行命令，见第 2 节的“复审者不能写文件时” |
| `general-purpose` | 宿主的通用子代理：一致性审用它；首选不可用时代码复审也用它 | 必须带第 2 节的任务书；代码复审时把上面那份定义文件的正文一并交给它 |

`product-dev:code-reviewer` 不在名单里时：把它加进项目配置是改闸门的行为，先得到用户同意（R2）；没有同意就改派 `general-purpose` 并按实际登记，不借用名单里别的名字。

安全专项（中高风险必做）：另派一个子代理，任务书里只留“安全”一个维度并附第 4 节的安全清单，它的发现并入代码复审报告的“发现”一节；改动很小时可以由同一个复审者一并做，报告里写明。

模型：按 R9，复审用的模型不弱于被复审内容的作者；作者是最强一档时，复审也用同一档。子代理定义文件里的默认模型偏弱，派发时把模型写在调用参数里，不依赖默认值；宿主不能指定模型时，在报告和汇报里写明实际用的模型。

## 2. 任务书

派发时把下面的任务书填好原样交给复审者。只有按这个格式出的报告才能通过登记。

> 你是独立复审者，没有参与这次改动的编写。只读不改，不修代码。
>
> 复审对象：`{仓库路径}`，分支 `{分支}`，对比基准 `{主干}`，最终提交 `{提交哈希}`（PR `{编号}`）。
> 改动意图：`{一段话：要解决什么问题}`。依据：`{功能契约、计划或 bug 描述的路径}`。
> 审查种类：`{代码复审 | 一致性审}`。风险档位：`{低 | 中高}`。
>
> 做法：先读依据，再读测试，最后读实现；不只看 diff，把改动函数的调用方、相关的校验和测试也读了。每条发现先对照调用方、已有的保护和测试核实，被它们排除的不报。改动之前就存在的问题与这次引入的问题分开标。没有发现就写没有，不为了凑数而报。
>
> 改动范围：改动的文件清单是 `{文件清单}`，完整差异在 `{差异文件的路径}`。
>
> 按 `{本文第 3 节的维度；中高风险加第 4 节；一致性审用第 5 节}` 逐项审，按第 6 节分级，按第 7 节的格式出报告。能写文件的把报告写到 `{报告路径}`，并在回复里给出该路径和一句话结论；不能写文件的把完整报告放在回复里。报告必须有“结论”一节，全文不少于 200 字。

填任务书时不写自己的结论和猜测，只给意图、依据和范围，避免复审者顺着作者的思路走。派发前由主对话把差异存成文件（`git diff <主干>...HEAD` 的输出，放在会话的临时目录），把路径和文件清单填进任务书：复审者不一定能自己运行 git。

复审者不能写文件时（`product-dev:code-reviewer` 就是这样）：主对话把它回复里的报告原样存成报告文件，一个字不改、不增不删，再按第 7 节核对和登记，并在汇报里写明报告是代为落盘的。回复里没有完整报告的，让它补全，不由主对话代写。

## 3. 代码复审的五个维度

| 维度 | 要回答的问题 | 重点看 |
|---|---|---|
| 正确性 | 代码做的是不是它声称要做的 | 与契约或任务是否一致；空值、空集合、边界值；错误路径；差一、竞态、状态不一致；测试测的是不是该测的 |
| 可读性与简洁 | 别人不问作者能不能看懂 | 命名；控制流是否直白；能否用更少的代码做到；抽象是否值得它的复杂度；残留的无用代码；硬塞进无关流程的新条件分支；同一种判断反复出现 |
| 架构 | 改动是否合乎系统已有的设计 | 是否沿用现有模式；模块边界；重复代码；依赖方向；功能专属的逻辑有没有漏进公共模块；重构是减少了复杂度还是只挪了位置；类型边界是否明确 |
| 安全 | 是否引入了漏洞 | 输入校验；密钥是否进了代码、日志或版本库；鉴权；查询是否参数化；输出编码；新依赖的来源与已知漏洞；外部数据是否当作不可信处理 |
| 性能 | 是否引入了性能问题 | 循环里逐条查询；没有上限的循环或取数；该异步的同步操作；界面不必要的重复渲染；列表接口缺分页；热路径上的大对象 |

“这些测试能不能拦住回归”用实验回答，不靠读：把改动新增的一个条件反过来，相关测试应当失败。复审者只读不改，所以在报告里指明“反转哪个条件、哪条测试应当失败”，由作者验证；反转后测试仍然全过的，记为一条发现，写明缺哪个用例。

指出结构问题时同时给出改法，例如：把一串条件分支换成显式的分派；合并重复分支；把编排和业务逻辑分开；把功能专属的逻辑移回它所属的模块；复用已有的公共函数；把类型边界写明；删掉只做转发的包装；把过大的文件按职责拆开。优先选能让整条分支或整层消失的改法。

改动规模：约一百行易于审清；约三百行在只做一件事时可以接受；上千行应要求拆分（整文件删除和机械重构除外）。还要看文件本身：小改动把一个已经很大的文件继续撑大时，先问要不要拆。重构和新功能混在一个 PR 里，要求分开。

新增或升级依赖的改动另查：现有的栈是否已能解决；体积；是否有人维护；已知漏洞；许可是否相容。升级要读变更日志，一次只升一个包，锁文件的差异也要看，锁文件不手改。

## 4. 安全清单（中高风险）

先花几分钟站在攻击者一边：不可信数据从哪些地方进来（请求、表单、上传、回调、第三方接口、模型输出、别的进程写下的值），哪些东西值得偷或破坏，每个入口能否被冒充、篡改、抵赖、泄露、压垮、越权。然后逐项查与本次改动有关的部分：

| 方面 | 查什么 |
|---|---|
| 密钥 | 代码、日志、提交历史里没有密钥；真实的环境文件已被忽略；示例文件只有占位值 |
| 认证 | 口令用 bcrypt、scrypt 或 argon2 哈希；会话 cookie 设了 httpOnly、secure、sameSite 并有期限；登录接口限流；重置令牌有时限且只能用一次 |
| 授权 | 每个受保护的接口都检查身份；每次访问资源都检查归属或角色；管理接口校验管理员角色；令牌校验签名、期限、签发者 |
| 输入 | 在系统边界用允许清单校验（长度、范围、格式）；查询参数化；输出编码；上传限制类型和大小并校验内容；跳转地址先校验 |
| 服务端取数 | 用户能影响的网址先过允许清单，拒绝内网和保留地址，不跟随跳转 |
| 破坏性操作 | 删除、移动、覆盖的目标路径：先解析符号链接，确认在允许的根目录之下且不是根本身，并有归属证据 |
| 数据保护 | 敏感字段不出现在响应和日志里；对外通信走 HTTPS；个人数据有明确用途、保留期限和删除途径 |
| 响应与跨域 | 安全响应头齐全；跨域只放行明确的来源，带凭据时不用通配；错误信息不暴露内部细节 |
| 依赖 | 包管理器自带的审计没有未处理的、可达的高危项；新依赖看过来源、维护情况和安装脚本；不自动执行强制修复 |
| 模型输出 | 当作不可信输入：不进 `eval`、查询、命令行、页面结构或文件路径；提示词不是安全边界，权限在代码里做；密钥和别的租户的数据不进上下文 |

涉及新的认证流程、新类别的敏感数据、新的外部集成、跨域配置、上传、限流、权限提升的改动，本身就要先经用户同意，复审时核对有没有这个记录。

## 5. 一致性审的三个维度

只审增量：本次 PR（或本周期）新增和修改的文档、规则、注释。

| 维度 | 找什么 |
|---|---|
| 矛盾 | 两处对同一件事说法不同；文档与代码、配置、闸门的实际行为不符 |
| 重复 | 同一内容写在两处；应当引用的地方复述了一遍 |
| 过时 | 指向已改名或已删除的文件、章节、命令；描述的是旧行为 |

## 6. 严重级别

| 级别 | 含义 | 作者要做的 |
|---|---|---|
| 高 | 安全漏洞、数据丢失或损坏、功能不可用、与已确认的需求或契约不符 | 合并前修完 |
| 中 | 会在真实使用中出错的缺陷、缺少关键测试、明显让结构变差的改动、影响体验或使用的问题 | 合并前修完 |
| 低 | 不影响正确性的改进：命名、小的简化、风格 | 按项目规则记录并安排，可不在本 PR 修 |
| 提示 | 供参考的信息 | 无需处理 |

先报影响大的：正确性和安全在前，结构问题其次，其余在后。一个结构问题加十条小毛病，重点是那个结构问题。能量化的量化，不把会上线出错的问题说成“可能有点小问题”；也不因为写法和自己习惯的不同就拦下一个确实让代码变好的改动。

## 7. 报告格式与登记

报告写在会话的临时目录里，不放进被审的仓库（它不属于被审代码，放进去还会改变代码树）。必须有下面四节：

```markdown
# 复审报告：<PR 或改动的标题>

审查种类：代码复审（或 一致性审）　复审者：<登记名>　模型：<实际使用的模型>
对象：<分支> @ <最终提交哈希>，基准 <主干>

## 范围
读了哪些文件（含 diff 之外的调用方和测试），哪些没读、为什么。

## 发现
| 编号 | 级别 | 位置 | 问题 | 触发条件或例子 | 建议改法 |
|---|---|---|---|---|---|
（没有发现时写“无”。已存在的问题在编号后标“既有”。）

## 作者的验证
作者声称跑过的测试、构建、手工验证，复审者核对到了哪些，哪些没有证据。

## 结论
通过（或 不通过）。一句话理由；高、中级问题的编号清单。
```

登记脚本 `review.mjs` 的要求，报告要同时满足：

- 复审者的登记名在允许名单内。
- 报告不少于 `modules.review.reviewMinChars` 个字（默认 200）。
- 报告里有 `reviewKeyword` 指定的词（默认是“结论”）。
- 要登记为 pass 的报告里，“结论”后面不能紧跟“不通过”或“未通过”（中间隔着冒号、星号、井号也算紧跟）。所以结论只写一次；引用旧结论时换个说法。
- 存在高、中级问题时结论写不通过，登记为 fail；修完后重新复审，出新报告再登记。

主对话收到报告后先打开核对（R9）：范围是否覆盖了改动、发现是否属实、结论与发现是否一致，然后才登记。登记命令按项目的复审流程，见 [process.md](process.md) 的“两种复审流程”。把报告摘要贴进 PR：复审记录是本机约定，公开的摘要才是别人能核对的证据。

对复审意见有异议时，按事实和数据、项目规范、工程原则、与现有代码一致的顺序判断；仍不能一致的交用户决定，不自行忽略高、中级问题。“以后再清理”不算处理：要么本 PR 修，要么按项目规则记录并排期。
