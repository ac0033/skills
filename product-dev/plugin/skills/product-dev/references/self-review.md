# 推送前自查

交付段“推送前自查”一步的清单，由作者（写代码的主对话）自己做。它不算独立复审（R7），不能用来登记复审结论；它的作用是让独立复审不必把时间花在作者自己就能发现的问题上。

像这段代码出了事要被叫醒的人那样看。重要性次序：正确、安全、扛得住真实负载、有测试、够快、够精简。

## 1. 先看懂

- 范围：本分支相对主干的全部改动（`git diff <主干>...HEAD`），加上还没提交的部分。
- 读完 diff 再读它碰到的代码：每个被改函数的调用方、它调用的函数、测试、说明文档。
- 走一遍真实流程：数据从哪里进来，存了什么，出去什么。
- 改动会弄坏它没碰的代码。签名、返回值或行为变了，就搜全部调用方。
- 从仓库里（说明文档、部署配置）找出预期负载：一个人跑的脚本，还是很多用户和进程同时用。按这个负载判断，并写明假设的是哪一种。

## 2. 逐项查

| 项 | 找什么 |
|---|---|
| 错误 | 结果不对、崩溃、漏掉的边界（空、零、最后一项、取整、时区）；被这次改动弄坏的调用方；只在一个调用方修了、共用函数仍然是坏的 |
| 风险 | 安全漏洞（注入、弱随机、密钥、对用户输入缺少检查）；数据丢失（吞掉的错误、写入顺序不对、缺事务） |
| 规模 | 一个用户没事、多个用户出错：先查后写的竞态、每个进程都重复做的工作、只增不减的内存或列表、逐条查询、大输入上的平方复杂度、本该共享却放在进程内的状态 |
| 缺测试 | 有风险的新逻辑（分支、解析、金额、安全、写数据、bug 修复）没有一个在它坏掉时会失败的测试 |
| 速度 | 明显变慢是问题；小的提速（热循环里重复的工作）是建议 |
| 精简 | 该删的：死代码、没人用的选项、猜测性的功能；该复用的：仓库里已有的函数（写出路径）；标准库或平台已经能做的；只有一个实现的抽象、没人设置的配置；必须一起改的近似副本，合并；一个函数做了几件不相干的事，按职责拆，不按行数拆 |

再过一遍本项目特有的几项：

- 改动只做了任务要求的事，没有顺手改无关代码。
- 每条验收条件都有测试或可重复的验证方法，并且实际跑过。
- 没有为了变绿而屏蔽检查、跳过测试、放宽配置或加豁免（R4）。
- 源文件的文件头说明和导出项说明齐全（闸门会查）。
- 没有留下调试输出、注释掉的代码、未使用的文件。
- 文档、索引、契约与代码一致；新文件的位置符合 [process.md](process.md) 的“文档与目录”。

## 3. 记下之前先核实

- 每条发现都要有具体的例子：“这个输入或情况导致这个错误结果”。举不出例子的不算发现。
- 回去重读那几行确认：调用方确实存在，值确实可能为空，代码确实没人用。
- 标了 `shortcut:` 注释并写明限制的捷径是已做的决定，不算发现，除非预期负载已经超过了它的限制。
- 改法取能解决问题的最小改动，优先能删代码的；不为解决它新增分层、框架或配置。
- 不记个人风格偏好和含糊的担心。

## 4. 处理与留痕

发现分三类：必须修（错误、安全、数据丢失、在预期负载下会坏）、应该修（有风险却没测试的代码、确实的慢、重复、职责混杂、不该存在的代码）、可以修（小的提速、更短的写法）。

- 必须修和应该修的，推送前修完；修完重跑相关测试。
- 决定不修的，在 PR 描述里写明是哪一条、为什么。
- 没能检查到的重要方面，写进汇报的“用户需知”。

自查做完进“机械闸门”。自查没有发现问题，也不能省掉后面的独立复审。
