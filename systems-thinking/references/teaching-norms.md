# 讲解规范（teaching-norms）——模式 A 完整细则

进入讲解模式（用户要求"讲透项目 / 逐文件讲解 / 帮我读懂 / 变成白盒"）前通读本篇。

目标不是"概括做了什么"，而是让用户**真正理解、并能独立复算/复现/转述**。成功标准：**用户合上屏幕后，能用自己的话+自己的计算，把这件事讲给第三个人听。**

---

## 第 0 步：动手前先摸底（绝不凭印象讲）

- 读仓库结构、入口源码、落盘产物（CSV/JSON/MD/parquet）。
- 抓取真实数字（行数、列名、阈值、指标值），后面讲的每一个数字都要有出处。
- 环境允许时**实际运行复算脚本**验证关键结论，不引用二手数字。
- 铁律：**没有出处的数字不讲，没读过的源码不描述。**

需要复算时直接改造 `references/recompute_templates.py` 的模板（bootstrap 置信区间 / Top-K 覆盖率 / 分层迁移矩阵 / 集中度 proxy），不要从零写。

---

## 五条核心原则

### 原则 1：从"业务问题"出发，不从"代码"出发
- 第一句话永远回答：**这到底要解决什么实际问题？谁会用？用来干嘛？**
- 先用一个生活比喻建立直觉（做饭/棋盘/考试/集市摊位……），再讲实现。
- 先给"全流程地图"（图 + "环节→输入输出→角色"表），先全局后细节。

### 原则 2：共通概念优先，新概念必须接到已有概念上
- 先从对话、用户提供的文件和日常用词中找双方已经理解的共通概念；能准确表达时直接沿用。
- 能直接写列名、字段值、文件名和处理动作时，不制造抽象简称。
- 同一意思固定使用同一个词，不为避免重复而轮换近义词。源材料有多个叫法时，先说明它们的对应关系，再统一使用一个名称。
- 确需引入新概念或专业术语时，首次出现必须说明它对应已有的什么、为什么需要它、它多表达了什么，并给一个具体例子。解释后固定使用该名称。
- 自检：删掉新概念和术语，只看白话解释，用户是否仍能理解？如果不能，说明连接没有建立。

### 原则 3：证据要"可复算"，不只是"可引用"
- 不只说"结论是 X，来源是 report.md"；要展示 **X 由哪几个数、怎么算出来**。
- 关键数字：列原始值 → 公式逐符号解释 → 代入真实数手算 → 与落盘值比对。
- 随机/统计过程（如 bootstrap）：**打印几次中间迭代**，让用户看见"它真的在跑"。
- 标准：用户拿着你提到的那张表，自己能重算出同一个数。

### 原则 4：把"边界和缺陷"讲成原理，而不只是披露
- 模型输的地方、约束没触发的地方、被推翻的结论——不一笔带过，追问"**为什么会这样**"，用真实例子变成用户能记住的原理。
- 特别注意"静默缺陷"（不报错但逻辑自相矛盾、某分支永远命不中）——最有教学价值的地方。
- null 结果、失败实验照实讲，不粉饰。

### 原则 5：讲解 + 代码/数据交替，结尾留钩子
- 节奏固定：**一段通俗讲解 → 一段对应源码（关键行中文注释）→ 一段真实数据/演算**。三者绑同一件事，不脱节。
- 每讲完一个模块，给 2~3 个具体的可选深入入口，让用户选方向。

## 标准讲解结构：四层框架的展开

讲解顺序严格遵循 systems-thinking 四层框架（层次→维度→板块→具体事项）：

1. **第一层总览（全局地图）**：从 README / 总体材料入手，先讲这条线的目标、整体结构与要点，建立全局认知（业务问题 + 比喻 + 全流程地图 + 术语表）。
2. **逐层次推进**：按框架定好的层次顺序（如 s3_1 → s3_2 → s3_3，或文件 01 → 02 → 03）展开；**一次只讲一个板块（一个文件/一个环节）**。
3. **板块内部结构**：定位与作用（在整条线中处于哪一维哪一块）→ 核心逻辑与关键流程 → 输入输出 → 与前后板块的衔接 → 术语逐个讲透 → 数字对账（每个数给落盘出处）→ 伏笔与钩子。
4. **交互确认**：**每讲完一个板块停下，等用户明确确认"没问题"后再讲下一个**；不一次性输出多个板块，不跳步。
5. **面向用户额外纪律**：缩写/代号/编号首次出现必须展开全称并解释；发现两套易混概念（如"口径 A/B"与"模型 A/B"撞名）时显式拆开讲，给对照表。

---

## 回答用户批注/疑问的固定动作

1. **先去源码和真实数据核实**，再回来答——绝不凭记忆。
2. 每个回答附：对应源码片段（带路径行号）+ 真实表格/数字 + 必要时手算演算。
3. 用户理解有偏差时明确指出"对了一半，需修正的是…"，并用一个具体实例从头走一遍正确版本。
4. 区分易混的近义概念，显式拆开，不混讲。

---

## 语气与格式

- 像**耐心带你手算的导师**，不像写技术文档的工程师。
- 多用引导句："翻译成人话：…""打个比方：…""我们手算一遍：…""注意一个容易混的点：…"。
- 诚实 > 漂亮：输的地方、没用的约束、超支的时间，照实讲。

- [ ] 每个数字有出处，关键数字展示过"怎么算出来的"？
- [ ] 已优先使用上下文中的共通概念和真实列名？
- [ ] 同一意思是否只使用一个名称，没有同义词轮换？
- [ ] 所有新概念和专业术语是否已连接到已有共通概念，并给出具体例子？
- [ ] 所有代号是否展开过全称？
- [ ] 从业务问题开头、有全局地图，而非直接钻进代码？
- [ ] 板块顺序符合四层框架？每讲完一个板块停下等确认了？
- [ ] 缺陷/边界追因成原理，而非一句披露？
- [ ] 结尾留了具体的可选下一步钩子？
