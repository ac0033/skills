# Systems Thinking（系统思维）

把任何系统性对象（项目 / 任务 / 代码库 / 数据流水线 / 文档体系）的**构思、计划、讲解、写作**统一到一张四层框架上。判断成功的唯一标准：**产出物（计划 / 检查清单 / 讲解 / 文稿）让接收方既能 30 秒抓住全貌，又能沿着框架逐块跟进、逐块验收；讲解类产出还要让用户能用自己的话 + 自己的计算复述给第三个人。**

---

## 一、核心框架：层次 → 维度 → 板块 → 具体事项

一切系统性内容，都按这四层组织，自上而下切分（先定层，再定维，再列块，最后落项）：

| 层级 | 定义 | 判据 | 项目实例 |
|------|------|------|----------|
| **第一层·层次** | 系统按推进顺序或结构切出的大段 | 一段独立、有明确起点与终点的推进单位 | S0 数据重构 → S1 EDA → S2 特征工程 → S3 建模 → S4 可解释性 |
| **第二层·维度** | 同一层次内按性质划分的观察面 | 彼此独立（MECE）、合起来覆盖该层次全部要点 | "数据处理"层次分五维：整体分布 / 单特征形态 / 缺失异常 / 相关性冗余 / 前后一致性 |
| **第三层·板块** | 维度下的功能块 | 一个板块 = 一类同质的主题或动作 | "整体分布"维度下：标签分布、样本失衡、时间稳定性 |
| **第四层·具体事项** | 板块内可执行、可验证的最小单元 | 有动作 + 有判定标准 + 有出处 | "标签分布：零值格占比 93.2%（出处 S1 报告）→ 选 Tweedie 损失" |

切分方向：**自上而下（演绎）为主**——先有全局骨架再填肉；**自下而上（归纳）为辅**——零散想法先记下，再归堆进框架。归不进任何位置的记为"待归类"，不许散落在外。

### 采用四层框架的理由（本 Skill 的立身之本）

1. **体现思考逻辑且覆盖全面**：逐层 MECE 切分后，每个想法都有唯一归属，杜绝"东想一个西想一个"的零散发散；框架之外冒出的念头，要么是遗漏，要么是越界，一眼可见。
2. **便于他人理解和跟进**：接收方随时知道"现在在第几层第几块"，可以逐块确认、逐块推进（讲解时每讲完一个板块停下等确认，计划时逐块验收），不会迷失。
3. **框架可复用、可迁移**：换一个项目，即使不能完全套用，也把"先套四层框架再裁剪"作为第一步尝试——比从零发散更快更稳；用不完的维度删掉即可，框架本身不报废。

各层的切分手法、常见维度库与反例，见 `references/framework-guide.md`。

## 二、全流程工作流（构思 → 计划 → 输出 → 自检）

### Phase 1 构思（不动笔）

1. **摸底，绝不凭印象**：先用工具读真实材料（仓库结构、源码、落盘产物 CSV/JSON/MD），抓取真实数字（行数、阈值、指标值）。铁律：**没有出处的数字不讲，没读过的材料不描述。**
2. **一句话核心结论**：用一句话写出本次要传递/达成的核心信息；写不出，不进下一步。
3. **受众画像**：接收方是谁、已知什么、关心什么、会追问什么。
4. **共通概念盘点**：从用户消息、用户提供的文件、真实列名和已有项目用词中提取双方已理解的概念；同一意思只选一个名称。能直接使用列名、字段值或处理动作时，不另造抽象词。确需新增概念或专业术语时，预先写清它与已有概念的关系和首次解释。
5. **四层框架切分**：定层次 → 每层定维度 → 每维度列板块 → 每板块落事项。所有待办、疑问、素材**归入框架对应位置**。

### Phase 2 制定计划（框架变成可执行清单）

6. **事项可执行化**：每个具体事项改写成"动作 + 判定标准"（做完怎么算对、拿什么验收）。
7. **统一排序**：层次间按依赖/时间排；同组内按时间、结构、重要性**其一**排，不混用。
8. **冻结关键参数**：对比基准、阈值、超参等在执行前书面冻结，执行中不偷改。
9. **冻结主要用词**：计划中的列、对象、状态和动作一经命名，后续步骤、验收标准、表格和报告使用同一名称。源材料有多个叫法时，先做一次对应说明，再统一使用选定名称。
10. **计划形态**：分层清单 / 检查表 / 里程碑概览，让接收方能照着执行、照着验收。

### Phase 3 输出内容（两种模式，可混用；输出结构本身也按四层框架组织）

**模式 A·讲解（白盒讲解规范）**——触发词如"讲透这个项目 / 逐文件讲解 / 帮我读懂"：
- 原则速览：从业务问题出发（先比喻+全流程地图）；术语进括号大白话优先；证据可复算不只可引用；缺陷与边界讲成原理而非披露；讲解+代码/数据交替、结尾留钩子。
- **节奏与结构**：讲解顺序 = 四层框架的展开——先讲第一层（全局地图），再逐层次 → 维度 → 板块推进；**每讲完一个板块（一个文件 / 一个环节）停下，等用户确认"没问题"后再讲下一个**，不跳步不连发。
- 完整规范（含回答用户疑问的固定动作、语气、自检）见 `references/teaching-norms.md`；复算模板用 `references/recompute_templates.py`；范文对照 `references/worked_example_teaching.md`。

**模式 B·写作（结构化写作规范）**——触发词如"写报告 / 改这篇 / 给个提纲"：
- 原则速览：结论先行、以上统下、MECE 分组、统一逻辑顺序、以读者疑问为起点、量化实证、图即结论（图标题写观点）。
- 四种交付模式：完整文稿 / 结构大纲 / 诊断反馈 / 改写示范；拿不准时先给结构大纲确认骨架再写正文。
- 完整规范（含序言写法、量化改写公式、铁律、自检）见 `references/writing-norms.md`；场景骨架套 `references/templates.md`；量化与图表选型见 `references/quantify-visualize.md`；范文对照 `references/worked_example_writing.md`。

**框架与两种模式的关系**：四层框架负责"内容的组织骨架"（讲什么、按什么顺序、归哪里）；模式 A/B 负责"表达的方式"（怎么讲、怎么写）。任何一次产出，先有框架再有表达。

### Phase 4 自检（交付前必过）

- [ ] 框架检验：每块内容都能明确归位到"层→维→块→项"？没有框架外散落点？
- [ ] MECE：同层/同维不重叠、不遗漏？
- [ ] 每个数字都有出处？关键数字展示过"怎么算出来的"？
- [ ] 共通概念：是否优先使用用户消息、文件和日常表达中已有的简单概念？
- [ ] 用词一致：同一意思是否始终使用同一个名称，表格、图和正文是否一致？
- [ ] 新概念：确需新增的概念和专业术语，是否说明了它与已有共通概念的关系？
- [ ] 具体优先：能直接写列名、字段值和处理动作的地方，是否避免了黑话和不必要的简称？
- [ ] 指代纪律：所有缩写/代号/编号首次出现已展开全称并解释？
- [ ] 结论先行（写作）/ 业务问题先行（讲解）？
- [ ] 缺陷、null 结果、失败实验照实讲、并追因成原理？
- [ ] 结尾留了具体的可选下一步？
- 交付前 30 秒速查卡：`references/cheatsheet_onepager.md`。

## 三、铁律（不可违反）

1. **不改事实，不编数字**：只重构表达与组织，不改变事实与数据；用户没给数字时反问索取，不得虚构。
2. **共通概念与指代纪律**：先读取当前对话和用户提供的文件，优先沿用用户已理解的概念及真实列名；同一意思固定使用一个名称，不为避免重复而换同义词。新概念、专业术语、缩写、代号和编号首次出现时，必须用已有共通概念说明其含义和关系；用户纠正过的名称立即停用。
3. **原始输入只读**：分析、讲解、整理类任务不修改用户的源文件与原始数据，产出一律写新文件或新位置。
4. **诚实 > 漂亮**：null 结果、失败实验、模型输的地方、约束没触发的地方，照实讲，不粉饰，并追问"为什么会这样"把它讲成原理。
5. **交互确认**：讲解与长计划推进时，按板块逐步交付、逐块确认；用户未确认不进入下一板块。
