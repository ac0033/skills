# /api：为项目暴露对外接口

参数：`$ARGUMENTS`

## 参数

参数是要提供的接口方式，可以从下表中选一个或多个，用逗号或空格分隔，大小写和中英文都可以：

| 值 | 含义 |
|---|---|
| `plugin` | 插件：把 skills、MCP server、hooks、子 agent 等打包成一个整体，一次安装 |
| `skills` | 一个或几个 `SKILL.md`，告诉外部 agent 什么时候用、怎么装、怎么调、怎么读结果 |
| `mcp` | MCP server：外部 agent 注册后，把项目能力当作工具调用 |
| `cli` | 命令行工具：安装后可以在脚本和 agent 里直接调用 |
| `api` | HTTP API，附 OpenAPI 描述 |
| `sdk` | 本项目语言的客户端库，包装核心能力或 HTTP API |

- **参数为空**：由 agent 按下面第一节的规则自己决定。
- **参数非空**：按用户指定的方式提供。
  - 如果调研发现指定的方式明显不适合，在方案里说明理由和建议，仍由用户决定。
  - 只选了 `sdk`、没选 `api` 时，SDK 直接包装核心代码。
- **无法识别的值**：先问用户，不猜。`skill` 按 `skills` 处理。

## 一、先调研，出方案，确认后才动手

1. **列出核心能力**：读项目的 README、AGENTS.md、入口代码和测试，写清每项能力的输入、输出、耗时、副作用，以及需要的密钥或配置。
2. **查已有接口**：项目里已经有 CLI、服务、MCP 或文档的，优先在它们的基础上补齐，不另起一套。
3. **参数为空时，选择接口方式**：
   - **需要多种组件配合时，用 `plugin`**：既要 skills，又要工具（MCP）或 hooks、子 agent 时，打包成插件，让使用者一次装齐。插件内部的 skills 和 MCP 仍按第三节的要求写。
   - **其他情况，从 `skills` / `mcp` / `cli` / `api` / `sdk` 里组合**：
     - `skills` 一般都要提供，因为外部 agent 靠它才知道怎么正确使用本项目。
     - `mcp`、`cli`、`api`/`sdk` 按实际情况选 1–2 个，看哪种与项目最契合、接入最方便。例如：
       - 能力适合 agent 在对话里逐个调用，选 `mcp`；
       - 适合在脚本、流水线或终端里批量运行，选 `cli`；
       - 需要作为服务被其他程序或远程调用，选 `api`；
       - 主要给同语言的程序嵌入使用，选 `sdk`。
   - 在方案里写明选了哪些、为什么，以及没选的为什么不选。
4. **给用户一份方案，确认后再实施**。方案要写明：
   - 采用哪些接口方式，以及选择理由；
   - 每个接口暴露哪些能力，名称和参数是什么；
   - 长任务怎么处理；
   - 用什么依赖；
   - 改哪些文件；
   - 怎么验证。

## 二、设计原则

- **一套核心，多个薄适配层**：所有接口调用同一个核心函数或服务层，不在各接口里重复业务逻辑。能力名、参数名、错误码和结果结构在各接口间保持一致。
- **长任务用“提交 → 查状态 → 取结果”**：耗时超过几十秒的能力，不在一次调用里阻塞到底。提供启动、状态、结果、恢复（如适用）几个操作，状态里带进度和心跳，避免调用方超时。
- **结果可机读**：返回结构化数据（JSON），并区分“成功”“部分成功”和“失败”，失败时给出原因和下一步建议。不把“文件已生成”说成“结果已验证”。
- **安全默认**：HTTP 服务默认只绑定 `127.0.0.1`；对外开放需要鉴权。密钥从环境变量或配置文件读取，不写进代码、文档和示例。有副作用的操作（写文件、调用付费 API、删除）在描述里写明。

## 三、各接口的要求

### plugin

- 按宿主的插件格式打包。以 Claude Code 为例：
  - 清单文件放在 `.claude-plugin/plugin.json`，写明 `name`、`version`、`description`；
  - 组件分别放在 `skills/<名字>/SKILL.md`、`agents/`、`hooks/hooks.json` 和 `.mcp.json`；
  - 插件里的 skill 以 `/<插件名>:<skill名>` 的形式调用。
- 只放实际需要的组件，因为插件启用后会参与每一次会话。能由 skill 或 hook 按需完成的，不做成常驻组件。
- **分发**：在仓库里提供 `.claude-plugin/marketplace.json`，使用者先运行 `/plugin marketplace add <仓库>`，再运行 `/plugin install <插件名>@<市场名>` 安装。开发时可以用 `--plugin-dir <目录>` 直接加载测试。
- 其他宿主（Codex 等）的插件格式不同，需要支持时查它们的文档，在同一份源文件的基础上适配，不维护多份内容。

### MCP

- 用官方 SDK（Python `mcp`，TypeScript `@modelcontextprotocol/sdk`），默认用 stdio 传输。
- **stdout 只走 JSON-RPC**：日志和进度一律写 stderr；子进程设 `stdin=DEVNULL`，防止子进程等待输入而卡住。
- 工具名简短、带统一前缀；描述写清楚什么时候用、输入输出是什么、有什么副作用、大概耗时。参数用 JSON Schema 写全。
- 给出至少一种注册示例，例如 `claude mcp add <名字> -- <启动命令>`，以及通用的 `mcpServers` JSON 片段。

### CLI

- 通过包配置声明入口：Python 用 `[project.scripts]`，Node 用 `bin`。安装方式如 `uv tool install`、`pipx install`、`npm i -g`。
- 每个子命令都有 `--help`；提供 `--json` 输出供程序读取。退出码：`0` 成功，非 `0` 失败，并在文档里列出含义。
- 进度写 stderr，结果写 stdout。

### HTTP API

- 用框架自动生成 OpenAPI（如 FastAPI），路径和字段名与其他接口一致。
- 提供健康检查接口；长任务按“提交 → 查状态 → 取结果”设计。

### SDK

- 薄客户端：一个类或几个函数，对应核心能力，带类型标注和 docstring。
- 和项目本体一起发布，或作为可选依赖（extras）。

### skills（供外部 agent 使用）

- 放在仓库的 `skills/<项目名>/SKILL.md`（采用 plugin 时放在插件的 `skills/` 下）。frontmatter 的 `description` 写清触发场景。
- 正文包括：
  - 能做什么、不能做什么；
  - 怎么安装和接入（插件安装、MCP 注册、CLI 安装、HTTP 启动，只写实际提供了的）；
  - 标准流程；
  - 怎么读结果和判断成败；
  - 常见错误的处理办法；
  - 什么时候应该交回给用户。
- 细节放 `references/`，`SKILL.md` 保持精简。

## 四、写进文档

- **README**：增加“接入方式”一节。用表格列出每种接口：适合谁、怎么安装或启动、一个最小可运行的示例，以及指向详细文档的链接。
- **AGENTS.md**（或项目给 agent 看的规则文件）：加一条，告诉通过接口调用本项目的 agent 先读 skill 或接入指南。开发本项目的规则和调用接口的说明分开写。
- 较长的说明放 `docs/`，例如接入指南、字段说明、错误码。
- 命令、参数、路径都要和实际实现一致。示例用占位路径，不写本机真实路径。

## 五、验证

- 每种接口至少一个冒烟测试，走真实的调用路径：
  - plugin 用 `--plugin-dir` 或本地市场实际加载一次，确认 skills、工具、hooks 都生效；
  - MCP 用客户端完成一次 `initialize` 和一次工具调用；
  - CLI 实际运行一次命令；
  - HTTP 实际发一次请求；
  - SDK 实际调用一次；
  - skills 让一个没有上下文的 agent 只读 skill 完成一次典型任务。
- 检查各接口对同一个输入返回一致的结果结构。
- 照着 README 的安装步骤在干净环境里走一遍（或说明没有走、为什么）。

## 六、汇报

用中文汇报：

- 提供了哪些接口、为什么这样选，各自的安装和调用方式；
- 文档写在哪里；
- 验证了什么、结果如何；
- 没有做的部分和原因。

不自动提交；需要提交时按用户的提交规则处理。

## 封装成指令（可选）

本 skill 适合封装成指令 `/api`，方便一键调用：

- 如果当前宿主里它还不是指令，agent 第一次按本文件工作时，**先问用户是否封装**；用户同意后再做，不自动封装。
- 封装方法：把本目录复制到宿主的 skill 目录，目录名就是指令名。Claude Code 是 `~/.claude/skills/`，设置了 `CLAUDE_CONFIG_DIR` 时是该目录下的 `skills/`；其他宿主见各自文档。
- **不封装也能正常使用**：让 agent 读取本文件，把参数写在任务说明里即可（相当于上文的 `$ARGUMENTS`）。
