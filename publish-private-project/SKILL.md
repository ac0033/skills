# Publish Private Project（私有项目首次公开发布）

目标：一个在本机私有开发的项目，公开后任何人看不到作者的本机信息、其他私人项目、单位与真实业务数据；仓库具备公开项目的常规配套；发布本身是一个有版本号、有标签、有 Release 的产品动作。

判断成功的标准：在 GitHub 网页上搜索仓库内的本机路径、私人项目名、邮箱得到零结果；CI 全绿；Release 页有安装包；个人主页能点进这个项目并看到它的状态。

## 一、先弄清四件事，再动手

1. **项目现在的形态**：是否已有远程仓库、提交历史多长、有没有标签与分支、构建产物是否进了版本库。用 `git remote -v`、`git log --oneline | wc -l`、`git tag`、`git ls-files | wc -l`。
2. **作者已有的公开习惯**：看他已公开的仓库用什么许可、提交邮箱是真实邮箱还是 GitHub 匿名邮箱、有没有 CONTRIBUTING / CI。有先例就沿用，不另造一套。用 `gh repo list <用户> --json name,licenseInfo`、`gh api repos/<用户>/<仓库>/commits`。
3. **公开的边界**：用户要公开代码与功能，还是也开放服务？没做完的部分（登录、部署、多用户）要在状态里写明。
4. **哪些决定只能由用户做**：仓库名、历史处理方式、演示数据里的行业痕迹是否保留。这三件先问，其余按先例决定并在计划里写明依据。

## 二、四路核查（并行做，分别出清单）

每一路都要给出 `文件:行号 + 原文` 的清单，并标严重级别：必须移除 / 应当移除 / 无碍。清单细则见 [references/audit-checklist.md](references/audit-checklist.md)。

| 路 | 查什么 | 典型藏身处 |
|---|---|---|
| 隐私与涉密 | 本机绝对路径、邮箱、姓名、密钥、单位与系统标识、真实业务数据（真实行数、哈希、内部 ID 格式、内部列名） | 文档、示例数据、测试夹具、notebook 输出、锁文件、**git 历史** |
| 无关文件 | 开发计划、进度交接、验证记录、性能脚本、只为旧配置兼容的薄壳、编码助手的本地配置 | `docs/`、`scripts/`、`.claude/`、`examples/` |
| 私人注释 | 记录历史而非含义的注释（"此前…现在改成…"）、写给作者或助手看的话、第一人称复盘、里程碑代号 | 代码注释、CHANGELOG、写法说明文档 |
| 公开配套 | LICENSE、CONTRIBUTING、CI、Release、真实仓库地址、状态说明、安全说明、打包元数据 | 仓库根目录、`pyproject.toml` / `package.json`、README |

**git 历史单独查**：`git log -p --all | grep -nE '<路径特征>|<邮箱>|<私人项目名>'`，`git log --all --diff-filter=D --name-only` 看曾经删掉的文件，`git log --format='%an <%ae>' | sort -u` 看作者信息。工作区干净不等于历史干净。

## 三、处理原则

- **先备份再动手**：`git bundle create ../<项目>-history-<日期>.bundle --all`，并把当前分支另存为本地归档分支。任何删除都能回来。
- **私人材料不删，移到仓库内的 `.notes/` 并 gitignore**：作者本机照常能用，只是不进版本库。不必维护"内部版 / 公开版"两套仓库，那是大公司才付得起的成本；个人项目一个公开仓库 + 私人笔记不入库 + 测试守住就够。
- **注释只讲含义，不讲历史**：能改写成"这段代码做什么、为什么这样定"的就改写，纯历史的删掉。历史属于 CHANGELOG。
- **CHANGELOG 面向读者**：保留每个版本的实质变化，去掉"用户说 / 用户要求 / 分支名 / 快照标签 / 这台机器"这类开发日记口吻；"起因"改写成问题陈述。不要保留一条"隐私清理"记录去列举曾经泄露过什么。
- **历史里有本机信息就用全新历史**：孤儿分支一条"vX.Y.Z 首次公开发布"提交。`git filter-repo` 逐条改写成本高，中文路径曾被转义损坏时更不可靠。旧标签不要推（它们指向旧历史）。
- **提交身份用 GitHub 匿名邮箱**：`<id>+<用户名>@users.noreply.github.com`，只在本仓库 `git config`。
- **规则写一处，测试守住**：新增一条"公开卫生"测试：遍历 `git ls-files`，断言文本文件不含本机路径、私人项目名、邮箱、密钥形状，版本号多处一致，私人目录在 `.gitignore` 里。CI 每次都跑，以后就不会再漏。模板见 [references/repo-scaffold.md](references/repo-scaffold.md)。
- **先私有推送验证，再切公开**：`gh repo create --private --source . --push` → 看文件清单与 CI → 打标签让 Release 工作流跑一遍 → 用户看过后 `gh repo edit --visibility public`。公开是不可逆动作，验证之前不做。

## 四、按产品发布来做

- **版本号**：本次公开改了文档、打包元数据、新增 CI，按 SemVer 升一个次版本；CHANGELOG 顶部新增"首次公开发布"条目，写明状态。多处版本号（包配置、`__init__`、前端 `package.json`、插件清单）同步。
- **标签与 Release**：推送 `vX.Y.Z` 标签触发 Release 工作流，构建安装包并附到 Release，1.0 之前标 pre-release，正文从 CHANGELOG 截取该版本段落。
- **状态名**：代码与功能公开、可本机安装试用、但服务未开放时叫 **公开预览（Public Preview）**。README 第一屏写明状态、没做完的部分、版本变化与安装入口；个人主页的项目表同步这一行与状态说明。
- **配套文件**：LICENSE（沿用作者惯用许可）、CONTRIBUTING（开发环境、改代码约定、发布步骤、提 issue 要脱敏）、README 补徽章、真实克隆地址、安全说明（密钥存哪、对外开放要带令牌、没有登录别暴露公网）、许可段。
- **CI**：在 Linux 与 Windows 两个平台构建前端、lint、跑测试；作者只在一个平台开发过的项目第一次上另一个平台常有路径假设，小问题顺手修，大问题限定平台并写进已知限制。

## 五、验证与收尾

1. 本地：lint 干净、测试全绿（含卫生测试；故意塞一个本机路径确认它会红）、前端构建通过、安装包在干净环境里装上并跑最小演示。
2. 远端：CI 两平台绿；Release 页有安装包且标 pre-release；网页搜索仓库内的敏感串为零；提交作者显示匿名邮箱。
3. 主页：项目表的链接可点，状态说明在表下。
4. 本机：编码助手的记忆 / 交接记录更新为"私人材料在 `.notes/`、仓库地址、发布流程"，以后不要再把本机信息写回仓库。

## 报告格式

按用户的汇报规矩：首屏先说做完了吗、公开了没有（还是等用户切换）；然后是核查清单里各路各多少条、怎么处理的；最后列还要用户做的事（切换可见性、推送主页）。全过程只用数据表与文档里已有的说法，不造新词。
