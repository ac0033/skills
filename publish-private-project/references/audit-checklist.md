# 核查清单：公开发布的额外判定

查什么、在哪查、怎么查，以 submit 技能的 [checklist.md](../../submit/checklist.md) 第一至三节为准（隐私与涉密、无关文件、写给自己看的注释），本文不重复。首次公开时在此基础上再做下面几件事。

## 1. 每条结论标严重级别

每一条都落到 `文件:行号 + 原文`，并标严重级别：

- **必须移除**：一旦公开就泄露；
- **应当移除**：不泄露，但暴露开发过程或私人项目；
- **无碍**：通用示例、公共端点、假密钥。

## 2. 常见误判（可放行，列进白名单）

| 命中的规则 | 可放行的情况 |
|---|---|
| 绝对路径 | JSON 里的转义（如 `"FINAL:\n"`）；文档里故意写的通用示例路径（如 `D:\work\我的项目`） |
| 密钥 | 测试夹具里的短假密钥（如 `sk-abcdef123456`）；公共厂商端点（如 `api.example.com`） |
| 单位与系统标识 | 公开品牌名、通用行业词 |
| 真实业务数据的痕迹 | 合成数据，前提是能指出生成脚本和固定的随机种子 |
| 历史式注释 | 领域词里的“旧版本 / 原来”（如数据版本 N-1）、“待决事项”这类产品概念、厂商分节注释（如 `# ---- Anthropic ----`） |

需要举例时一律用虚构值，例如系统代号 `project_in_xyz`、产品 ID `ABC-0000000001-V01`、行数 `123456`、源文件名 `销售明细20230101-20231231.xlsx`，不要照抄真实数据。

## 3. CHANGELOG 的改写规则

- 标题只留版本、一句话、日期，去掉“分支 main”这类信息。
- “起因：用户提两件事——”改成“起因：两个问题——”；“用户说项目还有点混乱”改成对问题本身的陈述。
- 删掉快照标签、提交哈希、“这台机器连不上”、其他私人项目的路径与 id、plans 文件名、“用户目录里的那份已同步”。
- 以前的“隐私清理”条目改成一句中性的“已跟踪文件里不再出现本机路径”，不列举泄露过什么，也不写“历史未重写”。
