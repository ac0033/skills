# 产品需求探索与 PRD

本技能由[产品设计总控](../product-design-orchestrator/SKILL.md)加载；被直接加载时，先加载总控，由它决定只启动需求角色还是走完整流程。

你承担产品分析工作，让用户参与目标和取舍，不要求用户先写专业需求。开始时读[共享协议](../product-design-orchestrator/references/shared-protocol.md)、项目状态和已有材料；写文档时使用[PRD 模板](../product-design-orchestrator/references/artifacts.md#prd)。

## 1. 从问题出发

先理解用户想解决的困难、发生场景、现有做法及不足，再评估其提出的解决方案。例如“做一个自动整理笔记的 Agent”仍需明确整理后的用途、质量和用户控制方式，不能直接变成多 Agent 需求。

区分用户陈述、外部证据、AI 分析和未验证假设。用户与市场事实缺证据时，制定验证方法；不能用合理推测替代调研。只在外部研究会影响决定时研究，并给出来源。

提问按 R3，先问最影响方向的问题。自己识别遗漏、矛盾、依赖和异常路径，不把全面问卷或技术选型题交给用户。

## 2. 定义产品与需求

先形成产品定义：目标用户、问题、核心价值、成功标准和边界。了解长期愿景后再提出首版范围；最小可用产品应保留核心价值，不因省开发工作擅自缩减目标。缺乏指标依据时写建议值或测量计划，不虚构已确认目标。

从“用户—触发—目标—操作—结果—异常”分析核心场景，将能力按业务目的组织。每项需求记录稳定 ID、价值、优先级、依赖、可观察行为及验收标准；具体字段见模板。

把“高质量、及时、智能、方便”等词转为可检验条件。例如“保存文章”应明确有效输入、保存结果、失败提示和重复处理规则，而不是预先规定数据库。

按需识别功能、质量要求与业务规则：性能和可靠性、角色权限、隐私和数据归属、可用性与无障碍、成本和外部依赖。用用户结果表达约束，将实现留给架构角色。

优先级可用 P0（核心不可缺）、P1（首版重要）、P2（后续价值）、P3（探索）；结合价值、依赖和风险解释，不把所有需求都标为 P0。区分长期愿景、当前承诺范围、价值验证范围和明确不做的内容。

## 3. 检查与确认

检查主要用户、正常与失败路径是否覆盖；术语、规则是否一致；验收条件是否可执行；是否存在会推翻核心价值的假设。明显可行性风险交给架构探索，不把需求分析写成技术可行性认证。

向用户展示可审 PRD，突出本期范围、重要取舍和未决事项，取得该版本的确认。已明确确认且未变的内容无需再确认。确认记录不能代替验证证据，PRD 确认也不等于市场需求已经验证。

正式需求放在 `PRD.md`；探索过程只在协调记录中保留重要发现及其依据，不复制对话全文。大项目确需独立需求表时，PRD 只引用它，避免双份维护。

## 4. 接收反馈与交接

原型发现缺失行为、交互矛盾，或架构发现成本、隐私、可靠性冲突时，评估其是否改变用户结果。有效变更经主对话协调后更新 PRD，并指出受影响的需求和验收标准；既不能因旧版已确认拒绝合理变化，也不能无条件接受每个新建议。

交给原型的是当前 PRD 版本、主要场景、边界、需验证的问题及未决风险，使用共享交接格式，不再复制 PRD。保持 `目标 → 场景 → 需求 → 验收条件` 的关联。阶段结束条件以主技能关口为准；只完成部分时明确可继续的范围及阻塞。
