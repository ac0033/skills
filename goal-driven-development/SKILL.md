# 以终为始的功能开发

先回答"做成什么样算好、拿什么证明"，再回答"怎么做"。

这份 skill 用得对不对，看一条：**交出去的结论，要能被一份事先写定、从未用来调优的测试集证明；证明不了时，如实说明差在哪、为什么、下一步做什么。**

## 总览

| 阶段 | 回答的问题 | 产物 | 谁拍板 |
|---|---|---|---|
| 一 目标与标准 | 做成什么样算好？拿什么证明？ | 目标、能力体系、评价标准与门槛、封存的测试集 | 用户 |
| 二 问题拆解 | 要达标，必须解决哪些问题？ | 问题树、每步的思路、推进顺序 | agent 提出，用户确认方向 |
| 三 找思路 | 每个问题用什么方法解决？ | 方案及出处 | agent |
| 四 验证集迭代 | 方案有效吗？有没有弄坏别的？ | 验证集、逐轮读数、开发日志 | agent |
| 五 测试集验收 | 换一批没见过的数据还成立吗？ | 验收报告 | 用户 |

阶段顺序不能颠倒。后面任何一步卡住，都可以回到前面的阶段，而且应该回去。

---

## 阶段一：目标与标准

1. **先摸底。** 读项目里现有的目标、文档、数据和历史结果，拿到真实的现状数字。已有的术语和约定直接沿用，不另起一套。
2. **把目标写成能判定真假的句子。** "更好用"不算目标。要能说清楚：在哪些情况下、和谁比、达到什么程度算成功。写不出判定方式，就回去和用户对齐。
3. **把目标展开成能力体系。** 目标拆成若干项能力，要求彼此不重叠、合起来能覆盖目标。每项能力配三样东西：
   - **主指标**：做到了没有；
   - **护栏指标**：为了做到，有没有弄坏别的；
   - **约束**：成本、时间、安全等不能越过的线。
   能力和实现手段要分开。先定"要什么能力"，"用什么手段"放到阶段三再想。
4. **定对照。** 至少要有一个不做改动的现状，外加业内常见的朴素做法。条件允许时再加一个理论上限做参照。只赢过弱对照，不能算提升。
5. **门槛在看到结果之前写定**，交用户确认。写定以后，不能因为某次结果回头改；要改只能由用户决定，并注明改前改后的结果不能直接比较。
6. **这一步就选好测试集并封存。** 只记录它的来源、规模和切分方式，不看具体内容。测试集和之后建的验证集不能有交集。
7. **举一反三。** 目标定下后，追问三遍：
   - 这个目标还隐含了哪些没列出来的能力？
   - 同类问题换个场景，会以什么形式出现？
   - 现有指标能不能测出这些形式？
   把答案补进能力体系，不要等到测试失败才发现。

→ 写法与模板：`references/goals-and-standards.md`

## 阶段二：问题拆解

1. **从标准反推结果由什么决定。** 把主指标拆成几个决定因素（例如"结果 = 信息拿到了 × 拿到后用对了"），用现有数据看哪个因素已经做到头。已经做到头的因素上再使劲，分数也不会涨；这一步决定力气往哪里用。
2. **拆到能验证为止。** 顺着"目标 → 能力 → 决定因素 → 具体问题"一层层拆。每个具体问题都写清五件事：影响哪项指标、现在是多少、目标是多少、怎么验证、依据是什么。拆不到能验证的程度，说明还没想清楚。
3. **从第一性原理出发。** 每一步追问"为什么必须这样"，一直问到事实或原理为止，不拿"别人都这么做"当理由。依据标上可信度：实测、文献、推断。推断越多，越要先做小实验确认。
4. **带全局约束的贪婪推进。** 每一步先做收益最大、代价最小、风险可控的问题，但任何一步都不能：
   - 违反约束；
   - 让已有能力变差。
   每做完一步，重新排剩下问题的优先级，因为上一步的结果会改变下一步的最优选择。
   贪婪法的风险是困在局部最优。出现下面任何一种迹象，就回到第 1 步重看决定因素：连续几步都在同一个指标上打转；某个改动要靠特殊处理才成立；改好一处总坏另一处。
5. **哪一块明显不达标、原因也已经清楚，就先解决它。** 不要攒到最后一起改。

→ 拆解手法与整体最优检查：`references/decomposition.md`

## 阶段三：找思路

1. **先判断是不是常见问题。** 大多数问题前人都做过，先查再动手，不要从零发明。
2. **只借鉴高质量来源。**
   - 论文看收录渠道、作者与机构、引用数和后续跟进情况、有没有可复现的代码与数据；
   - 开源项目看 stars、维护活跃度、作者或组织、有没有真实生产使用。
3. **借鉴思路，不照抄实现。** 写清四件事：原方法解决什么问题、要满足什么前提、我们的场景满足哪些前提、需要改哪里。前提不满足，照搬多半无效。
4. **方案要能推广到一类情况。** 检验办法：把方案讲给一个没看过失败案例的人听，他应该能明白为什么有效。如果解释时离不开某个具体案例，那是特判，不是方案。
5. **没有现成思路时，从原理推导。** 回到阶段二的决定因素，先推出方案必须满足哪些性质，再设计实现。

→ 来源筛选标准：`references/prior-art.md`

## 阶段四：验证集迭代

**验证集在问题拆解之后、动手实现之前建立。** 拆解完才知道每个问题该用什么来验证。验证集可以反复使用。

1. **按能力出题，不照着失败案例出题。** 每个要解决的问题对应一组题。每组既有"应该做到"的题，也有**护栏题**，也就是同一能力的反面。比如补了"该拒绝"的题，就同时补"说法不同、但其实应该接受"的题。
2. **先用现有实现复现问题。** 新题必须在改动前就能复现失败。复现不了，说明问题还没找准，回到阶段二，不要带着猜测去改。
3. **对照组只跑一次，存档。** 之后每轮只跑被测方案，并保持同样的条件对比。
4. **先快后慢。** 能自动判定的先自动判定，几分钟出结果；需要人工或模型判定的放后面。
5. **采纳标准，四条全满足：**
   - 新题通过；
   - 所有原有题组不变差；
   - 护栏题没有新增错误；
   - 约束没有超出。
   任何一组变差就否决，回到阶段三。
6. **先排除噪声，再下结论。** 差距可能来自随机性、判定标准不一致或评测工具本身的缺陷。先重复测量确认差距稳定；如果是工具缺陷，两边在同样条件下修好再重测。
7. **每一轮都写进开发日志：** 问题归到哪项能力、补了哪些题、改了什么、读数（带对照）、这一轮定下的事、否决的方案和原因。

→ 验证集设计、噪声排除与统计：`references/validation-and-test.md`

## 阶段五：测试集验收

1. **测试前确认：** 验证集全部达标、已有测试通过、代码已提交并记下版本号、门槛没有改动过。
2. **第一次测试：** 对照组和被测方案在同样条件下跑，按事先写定的门槛逐条判定。读数原样记录，以后不覆盖。
3. **达标：** 写验收报告，结束。
4. **不达标：** 不要照着测试集的具体题目去调。回到**阶段一**：
   - 看这类失败能归到哪项能力，现有标准能不能测出它。测不出，先补指标。
   - 然后重走阶段二到四：重新拆解、找思路；把失败的**类型**搬进验证集，在验证集上复现，不要把测试题本身搬进去。验证集达标后才能再测。
   - 测试集的失败情况只能看这一次，而且只用来归纳失败类型，不能拿来定阈值。
5. **第二次测试，也是最后一次：**
   - 比第一次好或持平：采用第二次；
   - 比第一次差：代码回滚到第一次测试时的版本，以第一次为准。
   - 仍然不达标：**停止迭代**，汇报两次中较好的一次。
6. **汇报必须包含：**
   - 两次读数，分开列，注明哪次之前看过失败情况；
   - 逐条对照门槛；
   - 没达标的项及原因，原因要归到能力和决定因素上；
   - 已排除的噪声；
   - 下一步建议，按预期收益排序，并单独列出需要用户决定的事。

→ 计划、日志与报告模板：`references/templates.md`

## 贯穿全程的纪律

- **从能力出发，不从个案出发。** 为某个失败案例专门调规则、加特判，就是过拟合。即使改完那个案例能通过，也不做。
- **测试集只用来验收，验证集才用来调。** 两者不混用。
- **评价标准不自己改。** 标准和门槛归用户所有。发现标准本身有缺陷，写明缺陷，交给用户决定。
- **出题、答题、判分分开。** 出题的、被测的、判分的不能是同一方，避免自出自判。
- **新改动不能弄坏原有能力。** 每次提交前，验证集全部不变差、已有测试全部通过。
- **宁可报错，不要静默降级。** 输入不合法或证据不足时明确失败，不给出不可信的结果。
- **质量、成本、效率一起报告。** 超出约束的方案，效果再好也不采纳。
- **如实记录。** 失败、没有提升、被否决的方案都要记下来。没测过的，不能写成"没问题"。

## 需要用户拍板的节点

- 阶段一：目标和门槛；
- 阶段二结束时：拆解方向；
- 阶段五：测试结果，以及是否进行第二次测试。

其余技术细节由 agent 围绕目标自行决定，不逐项请示。遇到代价取舍或方向变化时，简要说明问题和影响，再请用户决定。
