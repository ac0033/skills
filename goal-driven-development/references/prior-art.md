# 借鉴来源的筛选与使用

## 1. 什么时候先查

- 问题有通用的名字（去重、排序、冲突消解、缓存、异常检测、评测方法……）；
- 自己想了一轮没有清晰思路；
- 准备引入一个新的技术组件或算法。

## 2. 论文的质量判断

| 维度 | 看什么 |
|---|---|
| 收录 | 领域顶会、顶刊，或知名研究机构的技术报告。只有预印本时，看其他几项来补足 |
| 作者 / 机构 | 作者在该方向有没有持续工作；机构有没有相关积累 |
| 影响 | 引用数（按发表时间折算）；有没有被后续工作当作基线或沿用 |
| 可复现 | 有没有公开代码和数据；结果有没有被别人复现过 |
| 实验质量 | 对照是不是强基线；有没有消融；样本量和统计检验是否可靠 |

## 3. 开源项目的质量判断

| 维度 | 看什么 |
|---|---|
| 认可度 | stars、forks、被依赖数（看量级，不看小差异） |
| 维护 | 最近的提交和发布时间；issue 的响应情况 |
| 作者 / 组织 | 知名组织或领域内公认的作者 |
| 生产使用 | 有没有公开的真实用户或案例 |
| 许可 | 许可证允许我们这样用吗 |

## 4. 借鉴记录（每个方案写一份）

```
来源：<标题 / 仓库>｜<收录或 stars>｜<作者/机构>｜<链接>
它解决的问题：
它的核心思路（一两句话）：
它成立的前提：
我们的场景满足哪些前提 / 不满足哪些：
采用什么、改动什么、不采用什么（及原因）：
预期影响的能力与指标：
```

## 5. 注意

- 借鉴思路，不照抄实现。前提不满足时，照搬多半无效。
- 论文里的提升，是在它自己的数据和对照下得到的。搬过来之后，要在自己的验证集上重新证明。
- 多个来源说法冲突时，按上面的质量维度加权，并在验证集上做小实验判断。
