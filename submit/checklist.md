# 提交快照与同步仓库的检查清单

适用范围：任何项目在 **提交（commit）** 和 **同步到远程仓库（push）** 之前的检查。公开仓库与私有仓库都适用，公开仓库每一条都必须做。本清单不涉及版本发布（打标签、Release、安装包），那是另一件事。

原则一句话：**仓库里只放产品本身；本机信息、私人材料、写给自己看的话，一律不进版本库。**

---

## 一、隐私、个人信息与涉密信息

目标：任何人拿到这个仓库（含全部历史），看不到我的本机、我的其他项目、我的单位、真实业务数据。

### 查什么

| 类别 | 例子 | 判定 |
|---|---|---|
| 本机绝对路径 | `D:\…`、`C:\Users\…`、`/Users/…`、`/home/…` | 必须移除；文档里故意写的通用示例路径（如 `D:\work\我的项目`）可以保留，但要列进白名单 |
| 本机目录结构与工具数据目录 | 盘符下的一级目录名、编码助手的数据目录、plans / memory / session 文件名 | 必须移除 |
| 个人身份 | 邮箱、姓名、手机号、账号 ID、`"author"` 字段里的真名 | 必须移除；提交作者用 GitHub 匿名邮箱 `<id>+<用户名>@users.noreply.github.com` |
| 密钥与令牌 | `sk-…`、`api_key=`、`token=`、`Bearer …`、`.env`、`models.json` | 必须移除并撤销泄露的密钥；测试夹具里的短假密钥可以保留 |
| 单位与内部系统 | 单位名、系统代号、内部产品 ID 格式、内部表名与列名、内部目录命名 | 必须移除 |
| 真实业务数据的痕迹 | 真实行数、文件哈希、带日期的源文件名、金额、真实客户 / 供应商 / 商品 | 必须移除；合成数据要能指出生成脚本与固定随机种子 |
| 我的其他项目 | 其他仓库名、其他项目目录、平台里的项目 id、"某某项目已迁到…" | 应当移除，它们与本项目无关 |

### 在哪查（容易漏的加粗）

代码、文档、测试与夹具、示例数据、**notebook 的输出与 metadata**、**锁文件（uv.lock、pnpm-lock）里的私有源地址**、**编码助手配置（`.claude/`、`.mcp.json`）**、模板与插件清单、**git 历史（含已删除的文件与作者信息）**。

### 怎么查

```bash
git ls-files                                                    # 只查跟踪的文件
git grep -n -i -E '<路径特征>|<邮箱>|<私人项目名>|<单位代号>' HEAD -- . ':!uv.lock'
git log --all --diff-filter=D --name-only --pretty=format: | sort -u        # 曾经删掉过什么
git log --format='%an <%ae>' | sort -u                                       # 作者信息
git log -p --all | grep -nE 'sk-[A-Za-z0-9]{10,}|[A-Z]:\\|@gmail'            # 历史内容
git log --all --name-only --pretty=format: | sort -u | grep -Ei '\.env$|\.parquet$|\.xlsx$|\.sqlite$|models\.json'   # 数据与密钥文件是否提交过
```

**工作区干净不等于历史干净。** 历史里有本机信息时，公开前要么重写历史，要么用全新历史（孤儿分支一条提交）；已经公开的仓库一旦泄露密钥，撤销密钥优先于删提交。

## 二、无关文件：与产品功能或使用无关的一律不上传

逐个文件问三句：**用户运行产品需要它吗？贡献者改代码需要它吗？代码或测试在运行时读它吗？** 三个都"不"就不进版本库。

| 类型 | 例子 | 处理 |
|---|---|---|
| 开发计划、进度交接、验证记录、复盘 | `方案.md`、`进度交接.md`、`验证/*.json`、`plan.md` | 移到仓库内 `.notes/`（gitignore） |
| 依赖真实数据或本机环境的脚本与测试 | 性能脚本、`test_<真实项目>.py`、按环境变量才跑的测试 | 移到 `.notes/`，同时删掉 conftest 里的开关 |
| 真实项目的快照、样本 | `examples/<真实项目>/` | 移到 `.notes/`，文档里对它的引用一起删 |
| 编码助手生成或使用的文件 | `.claude/settings.json`、`CLAUDE.md` 草稿、会话导出、临时脚本 | 根目录那份取消跟踪并 gitignore；**注意只忽略根目录（写 `/.claude/`），模板目录里的同名目录可能是产品文件** |
| 只为旧配置兼容的薄壳、废弃入口 | "保留这个文件只为旧的 settings.json 还能用" | 删除 |
| 生成物与缓存 | `dist/`、`build/`、`__pycache__`、`.pytest_cache`、`node_modules`、前端构建产物 | gitignore |
| 本机运行态 | 平台目录、数据库文件、日志、`.venv` | gitignore |
| 被代码在运行时读取的目录 | 模板、skill、契约 JSON Schema、示例项目 | **保留**，它们是产品的一部分 |

`.gitignore` 至少要有：

```
/.notes/          # 开发者私人材料
/.claude/         # 编码助手的仓库本地配置（只忽略根目录）
.venv/
__pycache__/
dist/
*.bundle
```

## 三、注释与文档里写给自己看的话

注释只讲 **这段代码做什么、为什么这样定**；历史归 CHANGELOG，私事归 `.notes/`。

| 类型 | 识别 | 处理 |
|---|---|---|
| 历史式注释 | "此前 / 原来 / 之前 / 改成 / 迁移 / 兼容旧"，带版本号的说明 | 只留讲含义的半句，其余删掉 |
| 写给自己或助手的话 | TODO / FIXME / "记得 / 以后 / 暂时 / 先这样"，"用户要求 / 用户说"，"你" | 改写成规则，或删掉 |
| 第一人称复盘 | "我无法…"、"在本项目里查到的原因是…" | 改写成中性的规则依据 |
| 里程碑与内部代号 | M1、M2、"第几阶段"、内部项目名 | 删除代号，保留实质 |
| 调试残留 | 库代码里的 `print`、`console.log`、`debugger`、成段注释掉的代码 | 删除 |
| CHANGELOG 里的开发日记 | "用户说项目还有点混乱"、分支名、快照标签、提交哈希、"这台机器连不上" | 改成问题陈述与实质变化；不要保留一条"隐私清理"记录去列举曾经泄露过什么 |

**不要误伤**：领域词里的"旧版本 / 原来"（如数据版本 N-1）、"待决事项"这类产品概念、按厂商分节的注释（`# ---- Anthropic ----`）。

## 四、清理临时与中间文件，产物分门别类归位

提交的是一份**干净、有序的快照**，不是工作现场。提交前把工作区整理成别人一眼能看懂的样子。

### 清掉什么

| 类型 | 例子 | 处理 |
|---|---|---|
| 临时文件 | `tmp_*`、`test.py`、`新建文本文档.txt`、`*.bak`、`*.orig`、`~$*.xlsx`、编辑器交换文件 | 删除 |
| 中间产物 | 一次性的核对结果、调试导出、探索时落下的 csv / parquet、旧版本的产物副本 | 删除，或移到 gitignore 的 `.notes/` 或 `outputs/` |
| 重复文件 | `report_v2.md`、`report_final.md`、`report_final2.md` 并存 | 只留当前版本；历史交给 git |
| 生成物与缓存 | `dist/`、`build/`、`__pycache__/`、`.pytest_cache/`、`node_modules/`、前端构建产物、`.ipynb_checkpoints/` | gitignore，仓库里不放能重新生成的东西 |
| notebook 的执行输出 | 带着几百 KB 输出与图片的 `.ipynb` | 能重跑的清掉输出再提交；示例项目里刻意保留输出的除外，且要有说明 |
| 空目录与占位 | `.gitkeep` 撑着的空目录、只剩 README 的废弃目录 | 删除 |

```bash
git status --short --ignored | grep '^!!' | head        # 看看 gitignore 挡住了什么，确认没有该进的被挡
git clean -n -d                                           # 只列出、不删除：未跟踪的文件与目录
find . -name '*.bak' -o -name '*.orig' -o -name '~$*' | grep -v node_modules
git ls-files | xargs -I{} du -k {} 2>/dev/null | sort -rn | head        # 跟踪文件里最大的几个
```

### 本地与远程保持统一

原则上本地工作区与远程仓库保持一致：工作区里的每个文件，要么提交进版本库，要么写进 `.gitignore`，不留既没提交、也没忽略的文件污染工作区。提交完成后 `git status` 应当是干净的。

确实无法统一的（例如只能留在本地、又不适合忽略的文件，或本地与远程分支出现分叉），列出具体文件或分支和原因，向用户汇报，由用户决定，不自行绕过。

```bash
git status --short                                        # 提交后应为空；出现 ?? 的文件要么提交，要么进 .gitignore
```

### 产物归位：一个目录只装一类东西

目录约定定一次，写进 README 的「目录」一节，之后每次提交都按它归位。通用的分法(供参考)：

| 目录 | 放什么 | 不放什么 |
|---|---|---|
| `src/` 或包目录 | 源代码 | 脚本、数据、文档 |
| `scripts/` | 可重复运行的工具脚本（生成数据、构建、发布） | 一次性的探索脚本（进 `.notes/`） |
| `tests/` | 测试与夹具 | 依赖本机真实数据的测试（进 `.notes/`） |
| `docs/` | 面向使用者与贡献者的文档、契约、CHANGELOG | 开发计划、交接记录、验证记录（进 `.notes/`） |
| `examples/` | 可运行的示例，数据由脚本生成 | 真实项目的快照 |
| `templates/`、`skills/`、`plugin/` | 运行时读取的产品文件 | 草稿、旧版本副本 |
| `data/`（若有） | `raw/`（只读）→ `interim/` → `processed/`，大文件走 gitignore 或 DVC | 手改过的原始数据 |
| `.notes/`（gitignore） | 方案、交接、复盘、真实数据快照、私人脚本 | 任何产品需要的东西 |

文件命名一致：同一类文件同一种命名（全小写加下划线或统一的中文），日期用 `YYYY-MM-DD`，不用 `final`、`new`、`v2` 这类后缀标版本。
注意：文件位置如果变了，要检查是否会产生负面影响，如影响其他文件的引用

## 五、确定版本号

每次同步到远程的快照都要能说出它是哪个版本。版本号遵循 [SemVer](https://semver.org/lang/zh-CN/)：`v主版本.次版本.修订号`，例如 `v0.31.0`。

| 改了什么 | 升哪一位 | 例 |
|---|---|---|
| 修复缺陷、改文案、改注释，行为不变 | 修订号 | 0.31.0 → 0.31.1 |
| 新功能、新接口、新文档，向后兼容 | 次版本 | 0.31.1 → 0.32.0 |
| 不兼容的改动（契约、API、文件格式变了） | 主版本（1.0 之前：次版本，并在 CHANGELOG 写明不兼容） | 1.4.2 → 2.0.0 |
| 1.0.0 之前 | 接口随时可能调整，每完成一组功能升次版本，修复升修订号 | 0.x.y |

提交前核对：

- **多处版本号一致**：包配置（`pyproject.toml` / `package.json`）、包内 `__version__`、前端 `package.json`、插件清单——改一处就全改，用测试守住（见第九节）。
- **CHANGELOG 顶部有这个版本的条目**：一句标题 + 日期 + 实质变化；只写变化，不写"用户说"、分支名、本机情况。
- **版本号只往前走**：不复用、不回退；同步到远程之前发现写错了，改掉再同步。
- **不是每次提交都要升版本**：日常小提交可以先只提交；升版本的那次提交单独做、信息写 `vX.Y.Z · 一句话`，方便以后按版本回看。打标签与发布不属于本清单，见发布流程。

## 六、面向读者的文件要更新成"给远程查看的人"看的表述

README、文档、示例说明是别人打开仓库最先看的东西。它们的读者是**不在我电脑前、不知道开发过程的人**；提交前把这次改动涉及的部分改到与代码一致，且用对读者说话的口吻。

### 哪些文件要过一遍

| 文件 | 每次提交前核对 |
|---|---|
| `README.md` | 第一屏：这是什么、解决什么问题、当前状态；安装与运行命令能照着敲；功能说明与本次改动一致；目录一节与实际目录一致；链接都能点开（仓库地址、文档、Releases） |
| `docs/` 里的使用文档、接入指南 | 新增或改动的功能有对应说明；命令、参数、报错与代码一致；前置条件写全 |
| `docs/CHANGELOG.md` | 本版本条目已写（见第五节） |
| `CONTRIBUTING.md` | 开发环境、测试命令、约定与现状一致 |
| 示例项目的 README、模板里的说明 | 示例还能按说明跑通；模板文字里没有旧的命令或旧的文件名 |
| 代码里的 docstring、`--help` 文案、界面文字 | 与行为一致；不出现底层文件名和内部代号 |

### 表述上的要求

- **对读者说话**：读者是使用者或贡献者，不是我自己。"我这里…"、"本机…"、"上次…"、"按用户要求…" 这类话不出现；写"运行 `mytool ui` 后打开 http://127.0.0.1:8000"，不写"平台开着的话就能看"。
- **说现状，不说过程**：README 写"现在是什么样、怎么用"；"原来…后来改成…"归 CHANGELOG；"接下来打算…"归路线图一节或 `.notes/`。
- **命令与路径可复制**：仓库地址写真实地址不写 `<仓库地址>`；示例路径用明显的占位（`<项目目录>`、`D:\work\我的项目`），不用本机真实路径；每条命令说清在哪运行、运行完应该看到什么。
- **状态与边界写明**：项目处于什么阶段（见第十节的状态用词）、哪些还没做、哪些不支持，让读者不必试了才知道。
- **用词与代码一致**：功能名、命令名、文件名与代码里的一样，一个东西始终一个叫法；不造读者没见过的词。
- **不留占位与半成品**：`TODO`、`待补充`、`（此处后续再写）`、空标题、断掉的链接，要么补完要么删掉。
- **语言与格式一致**：全文一种语言风格（中文文档里保留必要的英文术语）；标题层级、代码块、表格风格前后一致；不用 emoji 堆砌。

### 怎么核对

```bash
git diff --stat main...HEAD -- README.md docs/          # 代码改了而文档没动，先问自己该不该动
grep -n -E 'TODO|待补充|此处|<仓库地址>|本机|我这里' README.md docs/*.md   # 占位与自言自语
grep -o -E '\]\(([^)]+)\)' README.md | sort -u          # 列出链接，逐个确认能打开或文件存在
```

有条件就在网页上（GitHub 的预览或本地渲染）看一遍 README，表格、图片、锚点链接在渲染后是否正常。

## 七、提交本身

- **提交身份**：仓库级 `git config user.name / user.email`，公开仓库用 GitHub 匿名邮箱。
- **提交信息**：说清改了什么、为什么；不写本机路径、私人项目名、"按用户要求"。
- **一次提交一件事**：清理类改动与功能改动分开提交，方便回看。
- **提交前跑一遍**：lint、测试、构建；有卫生测试（见下）的项目必须全绿。
- **看一眼 `git status` 与 `git diff --stat`**：没有意外的新文件、没有意外的大文件（超过几 MB 的二进制先问自己要不要进版本库）。

## 八、同步（push）前

1. `git ls-files | wc -l` 与上次比对，数量突变要解释得清。
2. `git grep` 一遍第一节的敏感串，应为零结果。
3. `git log --format='%an <%ae>' -5` 确认作者身份。
4. `git fetch` 后用 `git status -sb` 确认本地分支与远程的关系：只领先可以推送；落后或分叉时先向用户汇报，不强推。
5. 不推送归档分支、快照标签、bundle 备份：`git push` 只推当前分支，**不要用 `git push --all` / `--tags`**。
6. 推送后在网页上过一遍文件列表与 CI 结果；公开仓库再用网页搜索敏感串一次。

## 九、把规则写一处，用测试守住（若适用）

新增一个"公开卫生"测试（Python 项目放 `tests/test_public_hygiene.py`），每次 CI 都跑：

- 遍历 `git ls-files`，断言文本文件不含绝对路径、邮箱、密钥形状的字符串；
- 只有本机才知道的词（私人项目名、目录名、单位代号）放在 `.notes/hygiene_private_words.txt`，一行一个，测试读到就一并检查，词本身不进版本库；
- 断言 `.notes/`、`.claude/`、运行态目录在 `.gitignore` 里，且没有被跟踪；
- 多处版本号一致（如 `pyproject.toml`、包 `__init__`、前端 `package.json`），且 CHANGELOG 有该版本的条目。

放行清单（通用示例路径、假密钥）写在测试里，不靠人记。

## 十、同步项目状态到个人主页

仓库首次公开或状态变化时，同步个人主页仓库 `ac0033/ac0033`。首页 `README.md` 是由 `profile.yml` 生成的**产物**，不要直接改 `README.md`；项目链接、一句话说明、状态都改 `profile.yml` 里对应仓库的那一行。

状态只能取 `profile.yml` 顶部 `status` 枚举里定义的 key（显示文案由渲染决定，不要自己造词）：

| key | 显示 | 含义 |
|---|---|---|
| `active` | 已公开 | 可以正常使用 |
| `preview` | 🔍 公开预览 | 代码与功能已公开，可在本机安装试用；未完成的部分（如登录、部署）在脚注写明，暂不提供在线服务 |
| `wip` | 🚧 待更新中 | 只占项目名，仓库尚未公开 |
| `planned` | 🔒 未公开 | 已规划，暂不展示入口 |
| `archived` | 📦 已归档 | 已停止维护 |
| `deprecated` | 即将下线 | 保留一段时间后归档 |

在 `ac0033/ac0033` 里按顺序执行：

```bash
npm ci
npm run collect          # 采集仓库事实
npm run diff             # 看漂移，确认要改哪几行
# 编辑 profile.yml 对应的一行
npm run render           # 重新生成 README.md
npm run check            # 必须通过：README 与 profile.yml 一致
git add profile.yml README.md data/repos.json && git commit
```

只在仓库**真正可访问之后**才加链接，绝不把私有仓库写进主页；`npm run diff` 会以 `repo_missing` / `repo_private` 提示这类问题。若 `npm run check` 失败，说明有人手改了 `README.md`，以 `profile.yml` 为准重新渲染即可。首页仓库另有定时任务，会自动检测漂移并在需要时更新或开 Issue 提醒。
