# 工程流程（完整版）

本文是工程能力包的完整流程，按需读取。项目的 AGENTS.md 只保留流程地图（engineering-kit 标记块）和入口。
命令中的 `<kit>` 指本技能的 `kit/` 目录，`<项目>` 指项目根目录。

## 0. 原则

- 标准只有达标与未达标。做不到先调研替代做法，确实解决不了的如实列出交用户决定，不降级。
- 完成分状态（实现、CI、验收、已上线），每态有证据，不能互相替代。
- 活文档覆盖原文件，历史靠 git；记录类文档（ADR、验收证据包、发布记录）只追加。
- 能用脚本或钩子强制的，就不靠自觉。

## 1. 开工

1. 从最新主干新建分支。主干没有远程时，以本地主干为准。
2. 列出分支与工作树（`git branch`、`git worktree list`），确认没有遗留的未提交改动（WIP）。遗留的先提交、归档或清理，再开新任务。
3. 读项目 AGENTS.md 的流程地图与目录地图。
4. 按下面的“执行位置与排程”定好本任务的执行位置和顺序。

### 执行位置与排程

目的：用户在场的时间和本机的资源，留给需要用户参与、需要判断的工作；不需要人参与的重复性工作不占用这段时间，也尽量不占用本机。

前提：排程只决定同一流程里各项工作在哪里做、先做哪项，不改变流程本身。第 2–5 节规定的步骤、先后顺序、检查范围和通过标准一项不省、一项不降；排程与流程冲突时，按流程办。不为了方便调度而跳过、缩小、推迟到合并之后，或用较弱的检查代替。

工作分两类：

| 类别 | 包括 | 排在什么时候 |
|---|---|---|
| 创造性工作 | 需求澄清、方案、编码、处理复审意见、修复失败、需要用户决定的事 | 优先完成，排在用户在场的时段 |
| 重复性工作 | 全量测试、回归、端到端、构建、巡检、批量机械改动、跑闸门 | 攒成整块，在用户这一阶段要做的事做完、可以去忙别的之后一次跑完 |

“整块时段”是相对的，不指固定的钟点：凡是需要用户参与的事已经做完、用户可以离开的那一段，就是跑重复性工作的整块时段，白天、夜间都可以。一个任务可以分成几轮：创造 → 重复 → 再创造 → 再重复。每一轮先把需要用户的部分集中做完，再把这一轮的重复性工作集中跑完，下一轮的创造性工作以上一轮的结果为依据。

- 执行位置：开发和测试凡是能在云端会话执行的，都放到云端。云端不占本机资源，本机休眠时照常运行。
- 能放云端的条件：代码已推送到远程；不依赖只在本机才有的东西（未推送的文件、本机的数据库或服务、本机凭据、图形界面、硬件）。不满足条件的才留在本机，并在汇报里说明原因。
- 开工时定顺序：列出本任务的创造性部分和重复性部分。先做完创造性部分并提交快照；重复性部分排队，不穿插在中间打断。互不依赖的重复性任务合成一批。
- 用户在场时，本机只跑小范围的快速检查（与改动直接相关的单元测试、静态检查），供写代码时即时反馈。全量和耗时的检查放云端，或留到整块时段。
- 与闸门的关系：推送仍须有与当前代码一致的通过测试记录，复审、CI 与合并的先后照第 4 节，都不因排程而改变。在云端会话里开发的，闸门在云端跑、从云端推送；留在本机的，把“跑闸门、推送”放进本轮的整块时段。
- 每一轮整块跑完后集中汇报一次：通过与失败、失败的具体项、需要用户决定的事。失败不自行降低标准，修复属于创造性工作，放进下一轮用户在场的时段。
- 启动云端会话和定时任务属于有费用的外部动作，按第 10 节和项目的授权表执行。

## 2. 需求与方案

- 低风险改动直接做。中高风险（跨模块、新接口、数据库结构、权限、费用、服务器配置）先澄清需求，写功能契约，取得用户确认。
- 契约放在 `docs/04-开发/`，模板见 `docs/_templates/feature-contract.md`。契约定义“怎样证明正确”，验收标准不得擅自弱化。
- 实现中自行确定的口径要单列，待用户确认，不写成已决定。

## 3. 开发

- 测试先行：改源文件前，先写或补引用它的测试。测试随改动一起改。
- 注释：每个源文件有业务职责说明；导出的函数、类、常量前有说明（输入输出、异常、为什么这样做）。
- 目录：代码按语言惯例放 `src/`、`tests/`。新顶层目录须在白名单内：`layout.topLevelAllowed`，加上 `sourceGlobs`、`testGlobs` 里写明的顶层目录。

## 4. 测试、审查与合并（目标流程）

目标顺序：PR 前受影响测试 → CI → 独立代码复审和一致性审 → 合并。套件闸门的 `pr` 流程实现了“CI → 双审 → 合并入口”这一段（见本节末“套件闸门的两种流程”）；受影响测试选择尚未实现，推送前仍跑配置的 `testCommand` 全量。适配状态见 `../SKILL.md` 第 5 节；项目已有更完善流程时，以项目规则和实际闸门为准。

1. PR 前执行静态检查及受影响的单元、集成、端到端、视觉和安全检查；不能可靠判断影响范围时扩大范围或跑全量，说明选择及结果。测试用隔离环境和合成数据。
2. CI 对最终提交执行全量单元测试和项目适用的全量集成测试；端到端、兼容性、安全等检查按风险安排，明确跳过的理由。适用的必需检查通过后进入审查。
3. 按下方分档进行独立代码复审和增量一致性审（矛盾、重复、过时）；一致性审可以集中审多个 PR，但每个 PR 的最终提交、所做审查的结论及证据各自记录。合并前核对 PR、最终提交、CI 和该档要求的审查；提交或基线变化后重新核查受影响部分。
4. 审查发现的高、中级问题，以及影响体验或使用的问题在合并前修复；低级问题按项目规则记录并安排修复。本次引入的矛盾、重复和过时问题在本 PR 修复。同一 PR 三轮审查后仍需下一轮时，向用户说明问题、原因、已做处置和建议，等待用户决定。
5. 合并遵循项目规定与实际授权；不绕过失败的必需检查。`pr` 流程下合并只经 `merge.mjs`，它核对 CI 与两项审查都针对 PR 的最终提交；`pre-push` 流程的记录只证明推送前复审，不能证明 CI 后双审查或最终 PR 绑定。

审查频率按风险分档（风险分级见第 2 节）：

| 改动 | 代码复审 | 一致性审 |
|---|---|---|
| 只改文档（`reviewIgnore` 之内） | 不做 | 并入每周巡检（第 8 节） |
| 低风险小改动 | 每个 PR 合并前 | 可延期：并入每周巡检，或与其他 PR 集中审；延期要写明理由 |
| 中高风险 | 每个 PR 合并前 | 每个 PR 合并前 |

代码复审不攒到合并后：结论绑定 PR 的最终提交，合并后才发现的问题已在主干上，后续 PR 又叠在其上。一致性审可以集中审多个 PR，结论仍按 PR 各自记录。拿不准风险档位时按高一档处理。

套件闸门的两种流程（`engineering.config.json` 的 `modules.gate.reviewFlow`，命令在项目的 `scripts/engineering/gate/` 下）：

- `pre-push`（默认）：`gate.mjs` 通过后由独立子代理复审，`review.mjs pass|fail --reviewer <名> --report <报告> --summary "<一句话>"` 登记；推送时核对静态检查、测试记录和复审记录，三者都绑定当前代码树。合并按项目约定的入口。
- `pr`：`gate.mjs` 通过后即可推送，推送核对只要求静态检查和与当前代码一致的测试记录。CI 在 PR 最终提交上全部通过（每项检查成功、跳过或中性；一项都没有视为未通过）后按上表分档审查并登记，PR 未打开或 CI 未全过时拒绝登记：
  - 代码复审：`review.mjs pass|fail --pr <编号> --kind code --reviewer <名> --report <报告> --summary "<一句话>"`。
  - 一致性审：同上，`--kind consistency`；按分档可延期时用 `review.mjs defer --pr <编号> --kind consistency --reason "<理由>"`。
  - 合并：`merge.mjs <编号> [--method squash|merge|rebase]`。PR 打开、CI 全过、代码复审为 pass、一致性审为 pass 或延期、两份记录的提交都等于当前最终提交，才执行 `gh pr merge --match-head-commit`（默认 squash 并删除远端分支）；否则逐条列出原因，不合并。PR 又有新提交时记录过期，重新审查后再登记。
  - 只改文档的 PR（全部文件在 `reviewIgnore` 之内）按上表不做审查，合并入口只核对 PR 打开与 CI 全过；PR 文件列表为空或达到 100 个（`gh` 可能截断）时按含代码处理。其余 PR 合并入口不判断风险档位：代码复审必需，能否延期一致性审由登记者按上表判断。
  - 需要 GitHub 远程和已登录的 `gh`；没有 CI 的项目留在 `pre-push`。

## 5. 预发、生产与事故回归

- 预发使用与生产一致的发布产物，按风险执行核心流程、冒烟、验收、回归、视觉、兼容、安全、性能与负载检查；压力测试在专项环境按需进行。修改或修复后做针对性 sanity 检查。记录不适用项及原因。
- 发布前准备并验证回滚方案、上一版本与数据迁移的兼容性、备份和恢复路径；镜像回滚不等于数据恢复。按项目授权部署，小范围灰度和健康检查通过后扩大，生产持续监控，异常按授权和预案处置。
- 事故或测试漏检须调查为何测试和 AI 审查未发现、是否缺少测试或安全检查、CI 是否需要调整。将问题转成稳定、可重复的回归用例，放入适当阶段；无法自动化时记录原因、责任人和可执行的专项检查并跟踪补齐。可将事故、相关 PR、修复和回滚整理成脱敏样例，持续评估审查能力。

## 6. 文档与目录规则

| 类别 | 位置 | 规则 |
|---|---|---|
| 活文档（需求、架构、计划） | 阶段目录 | 原地覆盖，历史靠 git |
| 记录类（ADR、验收证据包、发布记录） | `docs/adr/`、`docs/acceptance/`、`docs/release/` | 只追加，不改旧文件（巡检会报错） |
| 模板 | `docs/_templates/` | 只读，复制后使用 |
| 阶段索引 | `docs/README.md` | 每个阶段目录都要登记 |

新建文件须满足以下之一：独立生命周期、独立被引用、独立时间点。并登记到所在阶段的 README。推送核对会拦截不在允许位置、又没有理由的新文件；理由写在豁免表 `newFiles` 中。

新建目录或文件的位置：

- 项目根目录之外：须先经用户批准，不得自行创建。说明要建在哪里、建什么、为什么，得到同意后再建。会话的临时目录（scratchpad）不在此限。
- 项目根目录之内：可以按上面的规则创建；任务完成后逐个检查本次新建的目录和文件，不必留下的全部清理（见第 7 节）。

大版本（例如 v2）才用新目录（如 `v2/`）；同一版本内不新建平行目录。

阶段目录：`01-原型`、`02-需求分析`、`03-架构设计`、`04-开发`、`05-测试`、`06-预发部署`（可在 `layout.stages` 中修改）。代码仍按语言惯例放在 `src/`、`tests/`。

## 7. 收工

1. 合并后删除远端与本地分支，清理工作树（`git worktree remove`）。
2. 列出本次新建的目录和文件（`git status`、`git diff --name-only --diff-filter=A <基准>`），逐个检查是否满足第 6 节；不必留下的清理掉。
3. 更新阶段索引（`docs/README.md`）。
4. 删除临时文件（scratchpad、导出物），不留在项目目录里。
5. 经验提炼（对应全局 CLAUDE.md 的“经验提炼”）：
   - 用户本人提出的决定或做法：直接记录到项目的 `practices/`（不跟踪）。
   - agent 总结的：只作为候选，列出标题、依据和建议归属，向用户确认后才记录或升格为能力。升格为能力时，写成变更集（见第 9 节），走同一条原子路径。
6. 汇报：完成情况、后续待办、用户需知、经验提炼，分开写。

### 经验记录

- 记录用户本人提出或采纳、跨项目可复用的决定、规则和解决问题的方法；项目特有结论仅提炼可迁移的做法。没有可记录的经验时不强行总结。已有条目更新而不重复；未采纳的 agent 建议不作为用户经验。
- 存在用户明确授权记录且需要新建时，在项目根目录使用 `practices/`；Git 仓库把该目录加入 `git rev-parse --git-common-dir` 下的 `info/exclude`，不跟踪、不提交。非 Git 项目直接创建。
- 按主题维护 `product-development.md`、`workflow.md`、`agentic-engineering.md`，以 `README.md` 索引；按实际需要创建。
- 每条记一条可迁移的原则、适用背景、要解决的问题、具体做法、可核实的实际效果和首次出处（项目、日期、例子）。效果未确认就写明，之后在原条目更新；再次验证可补充出处。
- 本轮有新增或更新时，汇报文件和条目；没有则如实说明。

## 8. 巡检（熵管理）

- 机械检查：`node <项目>/scripts/engineering/gate/hygiene.mjs`。检查顶层目录白名单、禁用文件名片段（copy、final、bak 等）、死链、阶段索引、状态合法性、记录类只追加、重复内容、空目录、超期草稿、已合并分支与残留工作树。
- 巡检只报告，不删除。删除文件须先列清单，经用户确认。
- 语义一致性审：由子代理只审增量（本次或本周期新增、修改的文档），找出规则与文档之间的矛盾、重复、过时。
- 周期：建议每周一次，或在大批合并之后。

## 9. 整包（一键复用、更新、回滚）

源仓库：`ai_agent/skills`（远程 ac0033/skills），整包目录 `engineering-kit/`。版本以标签 `engineering-kit-vX.Y.Z` 标记。

| 动作 | 命令 |
|---|---|
| 一键装进新项目 | `node <kit>/sync.mjs --target <项目>` |
| 只看计划 | `node <kit>/sync.mjs --target <项目> --dry-run` |
| 升级到当前整包版本 | 同上（同一命令） |
| 整包漂移检查 | `node <kit>/sync.mjs --target <项目> --check`（有差异退出码 1） |
| 回滚或安装到某个版本 | `node <kit>/sync.mjs --target <项目> --from-tag engineering-kit-v0.1.0` |
| 覆盖项目里有本地修改的套件文件 | 加 `--force`（先看冲突列表） |
| 检查整包可发布 | `node <kit>/tools/release.mjs --check` |
| 发布版本（提交整包目录并打标签，不推送） | `node <kit>/tools/release.mjs` |

同步是原子事务：先校验整包（清单、源文件、JSON），再统一写入，再冒烟测试，最后写锁文件。任一步失败，已写入的文件全部恢复原样。存在冲突时整包一个文件也不写。

变更集（反向提炼）：
- 用户本人的经验：`changeset.mjs propose` 登记后直接 `apply`。
- agent 总结的经验：先登记为提案，批量列给用户确认（推荐项在前），用户确认后才以 `--approved` 应用。
- 应用后运行套件测试；失败则整体恢复。应用后不提交，由 `release.mjs` 提交并打标签。

## 10. 授权边界

沿用项目 AGENTS.md 的授权表。推送功能分支、合并（经合并入口）、构建、预发部署属于常规动作；生产发布、回滚、数据恢复、破坏性迁移、密钥、服务器系统配置须单独授权。启动云端会话和定时任务（第 1 节“执行位置与排程”）有费用：授权表里写了的按表执行，没写的先问用户。整包发布只提交套件目录，不推送，不开 PR，除非用户明确要求。
