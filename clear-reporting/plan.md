# Clear Reporting 实施设计

状态：待审核；已根据跨平台、项目接入和可选依赖建议补充设计，尚未实施。核心目标是跨项目、跨模型复用汇报组织方式，不重设任何项目的执行阶段。

## 1. 为什么要分层

需要采用 evidence、knowledge model、narrative 的分工，但用具体职责约束它们，而不是只新增几个英文命名目录。

| 层次 | 保存什么 | 不负责什么 |
|---|---|---|
| 证据 evidence | 输出中实际观察到的事实、来源位置、统计范围、单位、验证方法及限制 | 不把解释或建议伪装成测得的事实 |
| 结论及依据 knowledge | 正在回答的问题、结论、证据引用、推断条件、反例、限制、决定与开放问题 | 不依用户偏好改变事实，不从局部结果推出全量保证 |
| 面向用户的解释 narrative | 背景连接、具体例子、概念引入顺序、数字读法、正文和证据链接 | 不自行创造新的项目事实或增强结论确定性 |

另有横跨解释过程的“用户用词与理解记录”：用户认可的叫法、具体含义、前置概念、已解释内容、仍有疑问的地方。它不是事实层，也不应与项目证据混写。

检查覆盖各层：程序查可确定的遗漏和引用，事实复核角色查事实与推断边界，独立读者查报告是否自足，用户反馈决定实际哪些地方仍需解释。

不要求一层一个 Agent。一个 Agent 可以分次处理，但写正文时仅取得当前问题所需的已核验材料，独立阅读检查使用不继承执行历史的上下文。无独立上下文能力时明确记录未执行独立检查，不冒充通过。

## 2. 最小例子：三层各有什么用

以下为虚构的软件工作示例，不是任何项目的实测结论。

证据：一个固定测试输入原来用时 8 秒，修改后用时 3 秒；记录输入、环境、测量方法及输出位置。

结论：这次测试输入的处理速度提高了。只测了这一种输入，不能证明所有任务都加快，也不能仅凭耗时变化证明原因。

解释：用户等待的这项操作，在这次测试中从 8 秒缩短到 3 秒，少等了 5 秒。其他规模的输入是否也会缩短，还没有验证。

如果用户不知道“延迟改善”是什么，直接使用“等待时间缩短”。只有需要与代码或文档对应时，再引入正式名称。原始事实、推断范围和具体说法分别保存，换模型后无需重新猜测它们之间的关系。

## 3. 通用部分与项目部分分开

工具包保存规则、格式、检查脚本和正反例。各项目保存自己的证据、结论、专业用词和理解记录。工具包不得混入任何特定项目的模型名称、阶段编号、指标阈值或审批制度。

拟议工具包结构（尚未创建）：

    clear-reporting/
      README.md
      plan.md
      skills/clear-reporting/SKILL.md
      core/workflow.md
      core/formats/
      core/examples/
      scripts/
      tests/
      adapters/
        generic.md
        codex.md
      .codex-plugin/plugin.json

skills 下只有一个主入口，按任务读取具体材料，避免一开始加载整套规范。运行所需知识必须自包含；已有 systems-thinking 等技能可用于实施时参考，不要求使用者已经安装它们。

项目侧拟议结构：

    reporting/
      evidence.jsonl
      knowledge.jsonl
      vocabulary.json
      understanding.json
      reports/<本次汇报>/
        explanation.json
        report.md
        checks.json

小任务允许单个 bundle.json 容纳这些不同部分，不为一句状态说明创建完整目录。规模大时再按任务分文件。无文件能力的 Agent 可使用同样的结构化文本，但不能声称已经持久化。

## 4. 能否用于其他 AI Agent

核心文件与工作流可以移植；不同平台能否直接安装同一插件，需要分别确认。

- 能读取文件和遵循指令：通过通用入口显式加载工作流及当前材料。
- 能运行 Python：执行不依赖模型服务的检查脚本。计划优先使用 Python 标准库；语言及版本在实现时冻结并测试。
- 支持 Skill 自动发现：按该 Agent 的加载位置安装 Skill；路径与格式应实测，不能一律假设相同。
- 支持独立会话或子 Agent：启用独立阅读检查。否则由新会话或人工检查补充，并标明状态。
- Codex：增加插件清单和入口适配。插件清单只是包装，不能进入通用工作流成为必要依赖。

实现中不硬编码 Codex 工具名、模型名、操作系统路径、memory 服务或收费 API。其他具名 Agent 的安装指南需在选定目标后查阅其官方文档并验证；当前不宣称已经兼容某个具体产品。

## 5. 用词和推理必须提前准备

用词记录至少有：首选名称、正式名称及别名、具体指向、必要前置概念、例子、含义边界、解释状态及用户反馈依据。

检查对象也包括普通中文抽象词，如“闭环”“信号”“口径”。不能只列英文术语。每个词需回答：具体是谁、什么记录、哪个动作、哪种关系。用户纠正的叫法在同一含义下持续沿用；不同概念不能为通俗而混为一谈。

理解状态分为未解释、已解释、用户确认、仍有疑问。模型自己讲过一次或用户同意继续，不构成用户已掌握的证据。

讲解材料按问题准备：为什么讨论、与前文关系、涉及对象、证据、数值读法、必要概念、例子、从事实到结论所需条件、限制、读完应能解释什么。

不得用“有重要意义”填充意义字段；缺少依据时留下明确缺口。假设例子单独标注，不能被读成真实结果。

## 6. 工作流与职责

1. 判断汇报规模：简单状态直接简明说明；涉及专业解释、数值推断或决策理由时使用完整流程。
2. 从产物提取当前问题所需事实，保留精确来源和验证范围。
3. 整理结论与证据关系，事实复核角色核对重要推断；不能只检查文件格式。
4. 结合用户用词记录，补齐逐问题讲解材料。
5. 逐块生成正文，再核对事实、范围、名称和数字。
6. 独立读者只凭报告回答问题并引用文中依据，防止靠自身知识补全遗漏。
7. 用户可以追问、跳过或继续；记录真实反馈，不每段强制考试。完整报告从核验材料组织，不能拼接运行日志。

执行日志默认留原处。影响正确性、复现或重要决定的失败保留在证据层；正文呈现其实际影响，避免讲述无关重试经过。理解所需背景和例子即使不改变决定，也应保留。

证据来源变化后，相关结论和报告需重新核对；保留替代关系，不能让旧知识无提示继续使用。

## 7. Skill、程序和 memory 各做什么

Skill 是调用入口和操作指南，负责分阶段取材料和处理失败。格式规定必须准备的信息。程序检查路径、字段、引用、单位、分母、已登记别名和来源变化；对抽象程度、解释正确性等只作提示，不声称自动证明可理解。

项目规则只需引用汇报入口，保留项目自身执行制度。Prompt 只传本次问题、用户目标和输出要求。Memory 为可选发现工具，只召回偏好或知识引用；文件是权威来源，不依赖特定 memory 实现。

不得把模拟读者通过写成用户掌握。不得把报告不清楚改写为实验失败。执行状态与汇报状态独立。

## 8. 怎样证明可复用

先选软件修改、数据分析、研究报告三类材料。每类包括陌生词、数字密集和过程噪声问题。固定事实、问题、评判依据，分开训练示例与测试样本。

比较同一模型在已有提示方式与新工具包下的输出，再比较不同模型。分别测试给定核验材料的写作能力，以及从原始产物到汇报的完整能力。模型选择和预算在测试前批准，当前不调用任何比较实验。

拟议验收：重大事实或范围错误为零；核心数字可追溯；关键问题有文内答案；前置概念未定义和名称混用均有记录及处理；用户指出的卡点在下一份材料中减少。统计逐项结果、耗时、重写次数和未通过场景，不用总分掩盖事实错误。

独立读者仍是模型，其通过不等于人类理解；最终应结合用户实际反馈。少量样本仅支持已测范围，不能保证所有模型与任务同样有效。

## 9. 实施批次

- 第一批只冻结通用格式与一份虚构端到端样例，确认分层及名称足够清楚。
- 第二批只将已确认流程封装为可复用 Skill 与最小检查程序，测试正常材料和明确错误材料。
- 第三批只完成跨任务、跨模型验证，据结果修正限制与适用范围。
- 第四批只完成选定平台的入口包装及安装验证，Codex 为一个适配目标，其他平台另列。

每批先给出明确产物和验收标准，经用户批准后执行。新目录独立于业务项目，不沿用 project2_final 的业务步骤编号。当前没有修改那个项目的实验、注册表或执行规则，也没有安装或发布插件。

## 10. 对原对话的取舍：只补能解决具体问题的部分

| 原对话中的建议 | 处理决定 | 落点与原因 |
|---|---|---|
| Evidence → Knowledge → Narrative | 保留 | 三种材料职责不同，避免从执行日志直接编报告 |
| Reader Model 与问题树 | 补充明确 | 写正文前确定读者目标、已有概念、根问题与必要子问题，补齐阅读顺序 |
| Data → Meaning → Consequence | 保留并加限制 | 数字先说明单位、范围和比较对象，再说明含义；不能为每个数字硬造业务影响 |
| 正确性与易懂性分两遍处理 | 补充明确 | 第一遍核对事实与推断，第二遍改变顺序、词语和例子；改写后再次比对事实，避免润色改变含义 |
| Relevance Gate | 改成信息去向判断 | 无关重试留日志；有效失败留证据；必要背景和例子进正文；不能只保留直接影响决策的信息 |
| 独立读者检查 | 保留但非必备服务 | 有独立上下文就用，无则允许用户另开会话或人工检查，并记录未完成项 |
| Memory Curator | 暂不单独实现 | 本地文件足以保存记录；memory 作为可替换检索入口，不增加独立服务 |
| 多 Agent、知识图数据库、复杂总分 | 暂不引入 | 先用简单记录和引用完成职责；没有证据表明这些组件是必要条件 |

“问题树”在简单汇报中可以只有一个问题。复杂报告才列子问题及依赖：某一节要回答什么、用哪些结论、读者需先理解什么。标题可以用自然语言，不强迫最终正文呈现机器字段。

不新增 Evidence、Knowledge、Narrative 之外的材料层。用户记录、问题顺序和检查是三层工作的辅助信息，不各建一个系统。

## 11. 工具包与项目的配合：约定输入输出，不接管项目

通用核心只规定需要什么信息、产生什么结果、缺什么就不能作什么保证。平台适配负责取得材料、运行检查和保存文件；项目接入负责告诉工具包哪里是权威产物，以及本项目有哪些固定叫法。

    用户的本次汇报要求
            ↓
    项目接入配置：输入来源、用词、输出位置
            ↓
    通用工作流：证据 → 结论 → 解释 → 检查
            ↓
    平台适配：读写文件、运行脚本、可选独立阅读
            ↓
    报告 + 引用记录 + 检查结果 + 待解释问题

### 项目首次接入

只需要提供或确认：项目标识、本次要讲的问题、权威输入位置、输出位置和当前用户目标。已有专业词表、历史理解记录、报告模板都可选。只有影响解释正确性的关键信息缺失时才询问，其他采用明确默认值。

项目接入配置建议使用 reporting/project.json，字段包括：

- project_id：隔离不同项目的证据、结论和术语；
- source_roots：允许读取的项目产物位置，不默认扫描整台设备或全部仓库；
- output_root：新汇报产物位置，默认不覆盖源文件和已有报告；
- authority：多个来源不一致时哪个是权威，未知冲突必须保留并询问；
- audience_ref：可选用户偏好及理解记录；
- vocabulary_ref：可选项目词表；
- report_entry：可选既有报告入口，用于后续确认发布到哪里。

一次请求提供 request_id、question、source_refs、audience_goal、detail_level 和可选覆盖项。多个 Agent 传递这些结构化材料及文件引用，不传一篇未经核验的长篇总结代替事实。

### 正常使用与返回值

项目按自己的流程完成工作，在需要汇报时显式调用本工具。工具返回：报告位置或报告正文、证据和结论引用、完成了哪些检查、尚缺什么、用户的未解问题。它不自行重跑项目实验、不修改业务结论、不推进项目步骤，也不把汇报状态写成项目完成状态。

发现来源冲突或数字缺乏依据时，保留缺口并请求核对；只阻止相关无依据判断进入最终结论，不让无关材料全部无法汇报。

事实层与结论层保留内部定位，正文用可理解的名称加就近链接。用户需要深入时能够直接进入证据，不必先理解整个仓库目录。

### 多 Agent 和升级

角色表示职责，不要求独立服务。单 Agent 可以分次完成准备、解释和复核，但检查记录必须注明是否独立。多人或多 Agent 写入时，先写各自 request_id 的独立材料，再由一个发布角色合并；禁止并发追加同一全局 JSONL 文件。没有锁或原子写能力时使用串行写入。

工具升级不能自动重写所有历史报告。配置、格式和报告记录版本，读取不支持的版本明确报错；迁移先保留原文件，再生成新文件。报告保存对应的来源指纹、用词版本及工具版本，便于知道为何发生变化。

卸载工具只移除入口或安装包，项目汇报材料仍可用普通文本工具阅读。项目事实不写入共享插件目录；跨项目通用偏好与项目专有知识分开，避免错误迁移。

## 12. 平台只需实现少量能力，不依赖具体工具名称

下列是拟议接口约定，不是已经存在的函数或可调用 API。核心表达所需动作，适配器再映射到宿主实际能力。

| 能力 | 输入与结果 | 没有时怎样处理 |
|---|---|---|
| 取得材料 read_source | 已授权引用 → 文本或表格内容、来源位置、版本信息 | 用户粘贴或附上材料；拿不到则标记缺少来源，不能声称核验 |
| 保存材料 write_artifact | 目标位置、内容 → 实际保存位置 | 输出可复制文本和恢复包，标明没有持久化 |
| 检查 run_check | 检查类型、材料 → 逐项结果 | 按清单人工/模型检查，标记未执行程序验证 |
| 独立阅读 review_fresh | 报告、目标、问题 → 回答及文中依据 | 用户另开会话，或保留待独立检查；同上下文自查不能替代 |
| 询问用户 ask_user | 当前缺口及简短问题 → 回答或待回复 | 在正文指出待答事项，不把沉默当作确认 |

返回状态统一表达成功、不可用、拒绝访问、执行失败，并附具体原因。能力可用性来自实际调用结果或宿主声明；Agent 不能因自己认识某个工具名而宣称可以调用。宿主拒绝时遵守拒绝，不自行绕过或升级权限。

最低使用形式是“能够接收文本并输出文本的 Agent”。这种形式可以使用组织方法，但没有持久化、来源自动读取和程序核验的保证。文件及运行能力可用后逐项增强；各模式保证不同，文档必须说明，不能宣传所有平台功能等价。

能力记录附在技术检查文件中，面向用户只解释影响本次理解或可信性的缺口，不在每份正文输出冗长的环境检查清单。

## 13. 所有增强能力都是可选项，并有最小使用方式

| 可选能力或服务 | 默认替代方式 | 是否阻止核心汇报 |
|---|---|---|
| Skill 自动加载 | 显式读取入口文档，或将必要说明粘贴给 Agent | 否 |
| Python/脚本执行 | 结构化材料与检查清单，明确机械检查未执行 | 否，但不宣称数值已由程序验证 |
| 独立子 Agent/新会话 | 导出独立阅读请求供手动发起，或人工检查 | 否，保留未独立检查状态 |
| memory/MCP 服务 | 项目内 vocabulary、understanding 与知识引用文件 | 否 |
| 其他写作 Skills | 工具包自带完成核心任务所需的规则和示例 | 否 |
| 向量检索或数据库 | 按问题、ID、标签和文件索引检索 | 否 |
| 联网或外部连接器 | 使用用户提供或本地可访问材料 | 否；没有来源不能核验相应外部事实 |
| 图形渲染 | 普通表格、文字流程和小算例 | 否 |

缺少服务时，不自动安装、不创建账号、不申请外部权限、不上传项目材料。若用户需要增强能力，提供对应官方安装资料、用途、需要的权限、验证方法和卸载方式。增加依赖必须有实际收益，不能因为工具存在就接入。

拟议安装指南分为：

1. 通用文本模式：阅读入口，提供本次问题与材料，按结构返回结果；完全不需安装服务。
2. 文件模式：复制工具包到选定位置，显式加载入口；设置项目输出目录；用一份示例验证读写。
3. 可选脚本模式：检查运行环境后执行工具包示例，分别验证正常材料通过、错误材料被拒绝。
4. 平台自动发现模式：按选定 Agent 的官方路径与格式安装入口，做一次真实加载测试；这只是简化调用方式。
5. 可选服务模式：单独说明接入 memory 等服务的方法、权限与替代方式。核心能力验证通过后才接入。

以上是指南设计，不提供未经验证的跨平台安装命令。正式实现时选定目标平台后，读取官方说明并验证命令，记录已测试版本与日期；未测试平台提供通用路径，明确未认证。

## 14. 进一步提升稳定性，同时控制复杂度

### 让材料可以中断、恢复和重用

每次任务保存当前问题、已核验引用、待补材料、已完成检查和下一动作。换模型或上下文结束后从这些材料继续，避免重新读长对话并再次解释成另一套词。没有写入能力时输出可复制的恢复包，但不声称下次能自动记住。

### 对新增信息设检查，不让解释越写越强

易懂性改写只能调整表达、顺序和已标明的示例。凡新增数字、因果解释、全量判断或建议依据，先返回证据/结论层检查。比较改写前后的主张和限定词，尤其是“可能→必然”“这个样本→所有情况”。这项检查直接防止通俗改写损坏准确性。

### 先检查一小块，不一开始重写整份报告

首次接入以一段真实困难材料验证用户用词和解释顺序。用户反馈后才应用到长报告；同一套解释已被认可时复用，避免反复创造新比喻。报告长短由用户问题决定，不以字段数量决定篇幅。

### 验收必须覆盖“缺少能力”的环境

测试除不同项目和模型外，还需覆盖无 memory、无其他 Skills、无脚本、无独立会话及仅文本输入等条件。检查是否能交付其能力范围内的报告，是否如实标记未完成检查，是否错误依赖某个特定平台 API。

拟议新增失败样例：来源已变、同名概念含义不同、数据来源冲突、JSON 格式正确但含义空洞、读者靠外部知识补全、重复运行导致知识重复、服务拒绝访问。测试逐项报告，不合成为一个漂亮总分。

### 限制重写开销

一次检查明确指出问题所在句、缺失材料与修复动作。拟定最多两轮定向修改；仍未通过时交付具体缺口和待决问题，不无限循环。每次记录耗时、模型调用和修改轮数，避免用高额隐性成本制造稳定的假象。

这些建议仍落在现有格式、工作流和检查程序中，不增加新的服务、材料层或独立 Agent。
